# 开发流程规范（tea）

> 定义"工作怎么走"。与 `编码规范.md`（怎么写代码）、`工程结构.md`（东西放哪里）配套。AGENTS.md 是总入口。

## 使用方式（触发条件）

- **任何开发任务**：先按复杂度×风险分诊（Fast=轻量路径 / Guided=全流程 / Controlled=全流程+先确认），再按 §一「流程路径分级」走对应路径。
- **任何开发任务**：按十阶段流水线推进，阶段 N 的 Quality Gate 未满足禁止进入阶段 N+1。
- **任务启动前**：先 request-analysis 收口需求（F 编号 + Given-When-Then + 澄清规则）。
- **编码/评审/部署**：分别触发对应技能，遵守 token 按需加载限制。

# 一、十阶段流水线

| 阶段 | 名称 | 使用技能 | Quality Gate（退出条件） | Output |
|---|---|---|---|---|
| 1 | 需求分析 | request-analysis | 需求文档已产出且用户确认：范围边界明确（做什么/不做什么）、F-编号需求 + Given-When-Then 验收、非功能约束、影响分析完整 | 需求文档（PRD 级）+ 影响分析 |
| 2 | 方案设计 | request-analysis | 细化方案经用户确认（D-编号决策点已拍板），技术选型有依据，红线冲突清零 | 细化方案 + 技术变更清单 + summary.md |
| 3 | 任务拆分 | request-analysis | 任务粒度 ≤ 4h，依赖关系明确 | 任务列表 + 执行顺序 |
| 4 | 编码实现 | coding-skill + biz-dev-skill 专项 | 遵守编码规范，红线零违反，编译 0 error | 可编译代码 |
| 5 | 单元测试 | unit-test-write + unit-test-ci | 覆盖率 ≥ 80%，核心逻辑 100%，测试全绿 | 测试报告 |
| 6 | 代码评审 | expert-reviewer（unit-test-ci 门禁覆盖 5-6） | 评审通过无 🔴 问题；CI 门禁全绿 | 评审记录 |
| 7 | 集成测试 | -（联调执行） | 接口联调通过，数据流正确 | 集成测试报告 |
| 8 | 预发验证 | deploy-verify | staging 环境验证通过（含冒烟） | 验证记录 |
| 9 | 上线部署 | deploy-verify | 部署脚本执行成功，冒烟通过 | 部署记录 |
| 10 | 线上观测 | deploy-verify | 30 分钟观测期无异常，指标在基线内 | 观测报告 |

## 阶段衔接规则

- 🔴 **串行推进**：阶段 N 的 Quality Gate 未满足，禁止进入阶段 N+1。
- 🔴 **需求分析先行**：阶段 1 必须先产出需求文档并经用户确认，才可进入阶段 2 方案设计；禁止跳过需求分析直接写方案（先方案后补需求会放大返工与确认成本）。
- 🔴 **确认门**：阶段 1 需求文档与阶段 2 细化方案均需用户确认后才进入下一阶段；需求文档含范围边界（不做什么）、F-编号需求 + Given-When-Then 验收、影响分析，方案含 D-编号决策点拍板。
- 🟢 **回退**：任一阶段失败，按下方回滚路线表回到对应阶段重来。

## 流程路径分级（Modification Level ↔ 十阶段）

> AGENTS.md §5 改动分级（L0-L3）是入口；十阶段流水线按级别裁剪，避免小改动走全套、大改动跳关卡。

| 级别 | 改动类型 | 流程路径 | 强制 Gate（不可省略） |
|---|---|---|---|
| L0 | 文档 / 文案 | **轻量**：阶段 1-3 合并为一次（summary 简版即可，无需独立需求文档），直接阶段 4-5 后阶段 6 快评 | 红线零违反 + 变更追踪（changes/ 或直接提交） |
| L1 | UI / 样式 | **轻量**：同上，但必须 type-check + build | 红线 + type-check + build |
| L2 | 业务逻辑 / 服务 | **全流程**：十阶段逐项，需求文档 + summary 不可省略 | 阶段 1 需求确认 + 阶段 6 评审 + 测试全绿 |
| L3 | 架构 / 数据模型 | **全流程 + ADR**：十阶段逐项 + ADR 先行 | L2 全部 + ADR + 迁移 upgrade/downgrade 往返 |

**小改动判据（L0/L1 轻量路径适用，全部满足才可合并阶段 1-3）**：
1. 无行为变更（改样式/文案/纯文档）。
2. 无接口契约、数据模型、迁移变更。
3. 改动文件 ≤ 3 个且不触承重墙（降级链 / 3D 状态机 / 同步逻辑）。
4. 不满足任一 → 走全流程路径。

## 阶段 4 编码纪律（引用编码规范）

- 40% 分批编码、批批验证：一次改动 ≤ 40% 总量 → 编译/测试 → 下一批。
- 编码中遵守 `编码规范.md` 红线 15 条；自检清单 26 项提交前逐项勾。
- 变更记录写 `changes/{feat-name}/summary.md`（与 git 分支同名）。

# 二、分支与提交规范

| 项 | 约定 | Example |
|---|---|---|
| 特性分支 | `feature/{feat-name}`，与 `.harness/changes/{feat-name}` 同名 | `feature/ai-tasting-assistant` |
| 修复分支 | `fix/{issue-or-bug-desc}` | `fix/brew-timer-rounding` |
| 主分支 | `main`（保护分支，只接受 MR 合入） | - |
| Commit | `type(scope): message`，type 用 feat/fix/refactor/test/docs/chore | `feat(record): 品鉴记录幂等提交` |
| 合并 | 经过阶段 6 评审 + CI 全绿后才可发起 MR | - |

- 🔴 **禁 force push main**；`push main`、发版、部署生产前必须按边界确认。
- 🟢 Commit subject ≤ 72 字符，body 讲 why；缺陷修复与功能/测试分开提交。
- 🟢 宽重构走 expand-contract：先 expand（新旧并存、CI 保持绿）→ 按包分批迁移（每批独立 commit）→ contract（旧形式无引用后删除）。

# 三、回滚路线表

| 阶段 | Rollback Strategy | Trigger |
|---|---|---|
| 编码实现 | `git checkout` 丢弃变更 | 编译失败 |
| 单元测试 | 修复代码 + 重跑测试 | 测试失败 |
| 数据库迁移 | 执行 `changes/{feat}/rollback.sql` | 迁移后应用异常 |
| 部署 | 回滚镜像 / 版本标签 | 冒烟失败 |
| 线上观测 | 走回滚路线回到预发 | 30 分钟内指标越基线 |

- 🟢 数据库迁移**必须** upgrade/downgrade 成对，往返测试通过才可提交（见编码规范 §27）。

# 四、多 agent 并行开发

> 原则：可并行则并行，不可并行保持串行；调度者（MainAgent/OrganizeAgent）是 scheduler，不是默认执行者。

## 适用场景

- **并行**：独立业务域（tea / record / culture / ware）各自成线；互不依赖的 pipeline 单元分片并行。
- **串行**：共享数据库迁移、跨域接口联调、3D 状态机改动（视觉层与状态层分离）。

## 调度纪律

- 🟢 每个 sub-agent 负责一个完整切片：获取 → 处理 → 验证 → 标准化输出；不做半成品交接。
- 🟢 **文件所有权 pre-assign**：分片前锁定文件清单（谁写哪些文件），禁跨权写他人文件；冲突文件（共享迁移/接口）归调度者串行处理。
- 🟢 **任务看板**：用任务列表（task_create/task_list）追踪每个切片状态；某切片超过 5 分钟无进展，调度者主动介入（查阻塞/重派/降级）。
- 🟢 共享输出 Schema 提前定好；分片结果由调度者汇总、去重、对齐来源。
- 🟢 阶段 gate（Oracle / 评审）在关键节点强制，不因并行而跳过。
- 🟢 任务进度文件 ≤ 80 行、原地重写不追加；结论一行 + 指向产物。

## 子代理（.claude/agents/，Claude Code 环境专用）

> **环境可用性**：`.claude/agents/` 是 Claude Code 子代理配置，豆包/doubao 环境不加载。豆包环境用等价技能/工具替代：code-reviewer → expert-reviewer；consistency-verifier → 评审维度 4（一致性）+ verify-harness.cjs；red-line-auditor → 编码规范自检清单。Claude Code 环境仍可加载三子代理。

| 代理 | 职责 | 触发 | 豆包环境替代 |
|---|---|---|---|
| code-reviewer | 6 维评审（正确性/性能/安全/一致性/可维护性/架构合规） | 阶段 6 | expert-reviewer（SKILL） |
| consistency-verifier | 代码 vs wiki 漂移检测（接口/模型/术语） | 阶段 6 前后 | 评审维度 4 + verify-harness.cjs |
| red-line-auditor | 红线扫描（编码规范 15 条） | 阶段 4/6 | 编码规范自检清单 26 项 |

# 五、代码 review

## 评审维度（expert-reviewer 6 维）

1. **正确性**：逻辑、边界、状态流转
2. **性能**：N+1 / 批量 / 缓存穿透 / 大列表分页
3. **安全**：SQL 注入 / XSS / 越权 / 脱敏
4. **一致性**：与 wiki 接口/数据模型/术语一致
5. **可维护性**：命名、抽象、重复、复杂度
6. **架构合规**：分层、依赖方向、红线

## 问题分级

| 级别 | 含义 | 处理 |
|---|---|---|
| 🔴 阻断 | 红线/安全/数据错误 | 必须修复，禁降级合入 |
| 🟡 主要 | 功能缺陷/性能风险 | 清零后才可过评审 |
| 🟢 次要 | 可维护性建议 | 记录即可 |
| 🔵 提示 | 风格/微优化 | 不阻塞 |

## 评审约束

- 🔴 红线问题禁止降级；🟡 未清零不过评审。
- 🟢 覆盖全部变更文件（不只 diff 部分）；评审记录落盘（阶段 6 output）。
- 🟢 评审不通过 → 回炉（按级别修复）→ 重新评审 → 通过后才进阶段 7。

# 六、skills 按需渐进式加载（token 优化）

> 目标：每次任务只加载必要技能，不预读无关技能，最大化 token 效率。

## 规则

- 🟢 **request-analysis 阶段**：上下文读取 ≤ 3 份（wiki 业务模型/接口协议/数据模型按需），禁止一次读全。
- 🟢 **wiki 选择映射（按改动面定，最多 3 份）**：
  | 改动面 | 必读 wiki |
  |---|---|
  | 前端页面/组件 | business-model + glossary |
  | 接口/服务（前后端契约） | api-contract + data-model |
  | 数据/表/字段 | data-model + glossary |
  | AI/agent/RAG | business-model + api-contract |
  | 纯文档/文案/样式 | glossary（可选，其余不读） |
- 🟢 **coding-skill 阶段**：技能上下文 ≤ 4 份（主技能 + 相关 biz-dev 专项），禁止整目录预读。
- 🟢 每个 SKILL.md frontmatter 首行一句话说明"这是干什么"，命中判断靠 description，不读全文。
- 🟢 任务完成即释放技能上下文，不跨任务保留。
- 🟢 探索性任务用只读手段（读目录/文件名/description），不污染主上下文。

## 技能族

| 族 | 数量 | 用途 |
|---|---|---|
| main-dev-skill | 8 | 主流程（request-analysis / coding / unit-test-write / unit-test-ci / expert-reviewer / deploy-verify / agent-eval / caveman-review） |
| biz-dev-skill | 19 | 业务专项（crud / 分页 / 文件 / 离线同步 / 3D / AI-agent / RAG / fallback / design-taste 等） |
| trouble-shooting-skill | 5 | 故障排查（慢SQL / OOM / CPU / AI 异常 / RAG 质量） |

> 数量以 AGENTS.md §12 声明为准，verify-harness.cjs 校验；本表用途供路由，不重复数数。

# 七、提交前验证矩阵

> 本地跑什么、CI 兜什么，边界在此。提交前必跑"本地必跑"列；CI 13 job 是 MR 门禁，最终兜底。

| 改动面 | 本地必跑（提交前） | CI 兜底（PR 自动） |
|---|---|---|
| 任意改动 | `npm run quality` + `node scripts/verify-harness.cjs` | 13 job 全绿才可 MR |
| 前端样式/组件（L1） | type-check + build | Biome / E2E / axe |
| 前端逻辑/流程（L2） | 上列 + `npm run test`；改流程/路由再加 `npm run test:e2e` | E2E / axe / npm audit |
| 后端旧栈（FastAPI） | `pytest` + `py_compile` | pytest / ruff + bandit |
| 后端新栈（Spring Boot） | `mvn test`（含 ArchUnit） | Maven 全量（Testcontainers） |
| 数据库迁移 | upgrade/downgrade 往返（真实 Postgres） | migration-test / compose-validate |
| 治理/文档 | verify-harness.cjs（ADR/CI/技能数/元信息） | harness-consistency job |

# 八、经验三级进化（lesson → pattern → instinct）

> AGENTS.md §13 维护规则的操作路径。三级晋升需人工确认，防错误经验扩散。

| 级别 | 判据 | 落点 |
|---|---|---|
| lesson（单次） | 一次踩坑，可能项目特有 | AGENTS.md §13 学习记录一行（AI 每次犯错加一行） |
| pattern（跨项目） | 同一问题 ≥2 个项目复现 | 写入 `docs/plans/patterns.md`（附 lesson 来源与日期） |
| instinct（自动生效） | pattern 验证后晋升 | 用户确认 → 更新 AGENTS.md 对应规则（注明来源与日期） |

**晋升流程**：Agent 在任务收尾时提出晋升建议（附复现证据）→ 用户拍板 → 落点文件更新。禁止自动跨级。

# 九、完成标准

- [ ] 十阶段 Gate 逐项满足（小改动合并场景：summary + 红线 + 冒烟不可省略）
- [ ] 分支规范符合（feature/fix + conventional commits）
- [ ] review 通过无 🔴、🟡 清零
- [ ] 多 agent 场景：分片结果已汇总、来源对齐、无重复
- [ ] 变更已追踪（changes/{feat-name}/ 三件套）
- [ ] 回滚路线明确（迁移成对 + 部署标签可回退）
- [ ] 观测期通过（30 分钟无异常）
- [ ] 跨会话任务已更新 HANDOFF（`docs/HANDOFF-YYYY-MM-DD-*.md`）
- [ ] 每周首次开工已跑环境审查清单（`docs/plans/environment-review.md`）
- [ ] 治理数字改动已同步 AGENTS.md + 对应规则文档（漂移当场修）
