# 需求分析技能

将模糊需求转化为清晰的技术任务，识别业务影响与技术风险，输出可直接进入编码阶段的需求分析报告。对应十阶段流水线**阶段 1-3（需求分析/方案设计/任务拆分）**。

## 触发条件

- "新增一个 xx 功能" / "给系统加一个 xx"
- "修改 xx 逻辑" / "xx 支持 xx"
- 收到任何新功能需求或变更请求，进入开发流程前
- **只要收到需求即触发，禁止跳过本技能直接编码**

## 前置准备

按需加载以下上下文（规则 + Wiki 合计不超过 3 个）：

| 上下文 | 何时读取 |
|---|---|
| `.harness/wiki/business-model.md` | 涉及核心实体/流程关系时 |
| `.harness/wiki/data-model.md` | 可能涉及数据库表变更时 |
| `.harness/wiki/api-contract.md` | 涉及新增/修改 API 时 |
| `.harness/wiki/glossary.md` | 需求中出现不熟悉的业务术语时 |
| `.harness/changes/` 已有 summary | 需求与近期特性可能重叠时 |

同时浏览 `backend/` 与 `src/` 目录结构，确认现有模块边界（见 `.harness/rules/工程结构.md`）。

## 执行流程

### Step 1: 需求解析
- **核心功能点**：动词 + 宾语描述（如"用户提交品鉴记录"），每个功能点独立编号 F1、F2...
- **功能边界**：明确做什么、不做什么（如"本次不做品鉴分享"），边界项同样列出
- **验收标准**：每条可验证（Given-When-Then），禁止"体验良好"这类不可验证表述
- **角色与入口**：哪些角色使用（游客/登录用户），入口在哪里（页面/接口/定时任务）

### Step 2: 影响分析
- **业务影响**：wiki/business-model 实体关系是否变化
- **技术影响**：数据模型 / API / 前端 / 部署（`.harness/changes/{feat}/summary.md` 写入）

### Step 3: 任务拆分
- 任务粒度 ≤4h，依赖关系明确，超出拆分子任务

## 澄清规则（命中任一必须提问，禁止自行假设）

1. 同一术语在需求与 `glossary.md` 中含义不一致
2. 涉及评分/系数/状态流转但未给出精确规则
3. 需求中"等"、"之类的"、"类似xx"的模糊指代
4. 隐含的非功能要求不明确（并发量级、数据量级、时效性）
5. 涉及承重墙（AI 降级链 / 幂等 / 评分模型）未确认影响
