# 需求分析技能

将模糊需求转化为清晰的技术任务，识别业务影响与技术风险，输出可直接进入编码阶段的需求分析报告。对应十阶段流水线**阶段 1-3（需求分析/方案设计/任务拆分）**。

## 触发条件

- "新增一个 xx 功能" / "给系统加一个 xx"
- "修改 xx 逻辑" / "xx 支持 xx"
- 收到任何新功能需求或变更请求，进入开发流程前
- **只要收到需求即触发，禁止跳过本技能直接编码**

## 前置准备

按需加载以下上下文（规则 + Wiki 合计不超过 3 个）：

| 上下文 | 何时读取 |
|---|---|
| `.harness/wiki/business-model.md` | 涉及核心实体/流程关系时 |
| `.harness/wiki/data-model.md` | 可能涉及数据库表变更时 |
| `.harness/wiki/api-contract.md` | 涉及新增/修改 API 时 |
| `.harness/wiki/glossary.md` | 需求中出现不熟悉的业务术语时 |
| `.harness/changes/` 已有 summary | 需求与近期特性可能重叠时 |

同时浏览 `backend/` 与 `src/` 目录结构，确认现有模块边界（见 `.harness/rules/工程结构.md`）。

## 执行流程

### Step 0: 模式与复杂度判定（先定这两项，再解析需求）

**模式**（先确认，越权写入是本技能最大风险）：

| 模式 | 边界 |
|---|---|
| 起草 | 依材料生成内容；缺口靠追问，不靠猜测补齐 |
| 授权修改 | 只改用户指定的范围；范围外问题提示但不顺手重写 |
| **只审校** | **不改源文件**；输出问题位置 + 短证据 + 影响 + 建议，不擅自统一争议口径 |

**复杂度**（决定说明深度，不自动加章节）：

| 档 | 判据 | 篇幅 |
|---|---|---|
| A 微调 | 沿用既有流程的局部文案/字段/展示/校验调整；同句文案同步多端仍可为 A | 可短至半页 |
| B 模块级 | 边界清楚的单模块或局部流程变化，关键规则模块内闭环；多页面不自动升 C | 按模块 |
| C 耦合 | 共享对象/跨角色状态/跨模块责任相互影响，需集中定义共同口径 | 完整 |

> 判据按**改动范围 + 规则耦合**定，不只数页面/端/角色。与 §5 Modification Level（L0-L3）交叉参考：C 档通常 ≥ L2。

**开工前已实现检查**（写 F 编号前必做）：
- `git log --oneline -10` 看最近提交（AGENTS.md §4 第 0 条）。
- **按领域概念 Grep 代码**（不只看 commit message）：用需求核心名词在 `src/`、`backend/src/` 搜，命中即读现有实现。
- 查 `docs/plans/out-of-scope.md`——命中被拒条目 → 不重新立项，附推翻理由再说。
- 已实现 → 补缺验证，禁止从零重写。

### Step 1: 需求解析
- **核心功能点**：动词 + 宾语描述（如"用户提交品鉴记录"），每个功能点独立编号 F1、F2...
- **功能边界**：明确做什么、不做什么（如"本次不做品鉴分享"），边界项同样列出
- **验收标准**：每条可验证（Given-When-Then），禁止"体验良好"这类不可验证表述
- **角色与入口**：哪些角色使用（游客/登录用户），入口在哪里（页面/接口/定时任务）

### Step 2: 影响分析
- **业务影响**：wiki/business-model 实体关系是否变化
- **技术影响**：数据模型 / API / 前端 / 部署（`.harness/changes/{feat}/summary.md` 写入）

### Step 2.2: 术语与决策沉淀（盘问产物当场落盘，不批量）

需求解析过程中术语/决策一旦 crystallize，当场写回，不攒到最后：

- **术语冲突当场指出**：用户用词与 `.harness/wiki/glossary.md` 已有定义不一致 → 直接说「glossary 定义 X，但你这里指 Y，哪个对？」，不等 frontier 阶段才提。
- **模糊/overload 词当场 sharpen**："账户/用户/订单"这类一个词干三件事 → 提议精确 canonical 词，用户确认后定。
- **术语定了当场写 glossary.md**：不批量补。glossary 只放领域语言，不放实现细节（不是 spec/草稿纸）。
- **跨代码校验**：用户说的行为与代码实际行为矛盾 → 当场指出，不按用户说的写 summary。
- **ADR 三条件全满足才写**（缺一跳过）：①难逆转 ②没上下文未来读者会困惑"为什么这么做" ③真实权衡（有替代方案且选了一个）。三缺二以下不写 ADR，直接进 summary。

### Step 2.5: 就绪度审查（开发前缺口扫描）

产出需求文档后按 8 维扫「能不能据此开工」，任一维含糊 → 补进影响分析或提问，禁止带缺口进编码：

| 维度 | 查什么 |
|---|---|
| 流程 | 主流程 + 异常流程完整 |
| 状态 | 状态流转 + 边界/终态明确 |
| 权限 | 谁能做什么（游客/登录/管理员） |
| 字段 | 类型/校验/来源/默认值 |
| 交互 | 前端行为与反馈（含五态） |
| 异常 | 失败/降级/重试路径（承重墙降级链） |
| 数据 | 模型/迁移/离线同步（sync_status） |
| 验收 | 每条 Given-When-Then 可测 |

### Step 3: 任务拆分
- 任务粒度 ≤4h，依赖关系明确，超出拆分子任务
- **上手既有工作先取证**（任务交接/接手历史任务时）：路径、文件名、数字、状态一律回查磁盘与 git，禁止凭对话记忆或上份交接转抄；与磁盘不符的项优先核实（该项即「交接后被改动」处）；查不到写「待核实」，不估算当事实。

## 澄清规则（frontier 提问）

8 维就绪度扫出的含糊点，**攒成一轮带推荐答案的编号清单**一次性问完。禁止命中一条问一条、多轮来回。

### 触发信号（任一命中即进 frontier 清单）

1. 同一术语在需求与 `glossary.md` 中含义不一致
2. 涉及评分/系数/状态流转但未给出精确规则
3. 需求中"等"、"之类的"、"类似xx"的模糊指代
4. 隐含的非功能要求不明确（并发量级、数据量级、时效性）
5. 涉及承重墙（AI 降级链 / 幂等 / 评分模型）未确认影响
6. 两个合理实现路径代价差异 >1 人日
7. 依赖外部数据/接口但口径未定（mock 还是真实数据）
8. Step 2.5 八维表任一格标"含糊"

### 输出格式

一次性列出，每条三要素，用户点头/改即可：

```
Q1. <问题一句话>
    推荐：<带默认值的答案，附一句理由>
    影响：<选 A vs 选 B 各牵动什么>

Q2. ...
```

### 纪律

- 一轮问完，最多 5 条；超出说明需求过大，先拆子需求再回来。
- 每条必须带推荐答案——不给推荐就是把决策成本甩给用户。
- 问题能通过读代码/wiki 自己回答的，**不要问用户**，清单里写"已核实：`<路径:行号>`"。
- 用户回复后答案固化进 summary.md；未回答项列"待确认"，禁止默认按推荐值往下做。
- 单人项目不做 relentless 长盘问；frontier 一轮即收敛，剩余模糊点走"假设说出口"（AGENTS.md §2）。

### 未知项处理（并行推进，不因局部未知冻结全局）

1. 只把**会改变范围/业务规则/用户可见行为/交付结果**的未知列为确认问题；排版/实现细节自己定，不转嫁用户。
2. **核心未知**（范围/权限/计算/关键状态/主要交互）未确认前，**暂停依赖该决策的部分，继续不依赖它的部分**——不因一个未知冻结整个需求。
3. 未回复、超时、跳过、"先继续"，**都不等于同意**，也不等于接受推荐值。
4. 只有用户明确说"此问题待确认"才允许以"待确认"进入 summary；须记问题编号 + 影响范围 + 用户原话；核心事项即使暂缓，也只能交付范围受限的草稿，不得声称可全部实施。

## Token 约束

- Wiki 上下文 ≤3 份，按"何时读取"列按需加载，禁一次读全
- 已编号需求不再重复解析
