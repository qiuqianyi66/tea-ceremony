# 调试问题提示词（debug-issue）

排查场景的可复制提示词。**本技能只产出提示词**；排查纪律对齐 `.harness/skills/trouble-shooting/00-bug-diagnose`（六阶段，Phase 1 是本体）。

核心信条：**没有能稳定复现的命令，就不许 theorize**。读代码猜根因是本技能要防的失败模式。

## 触发条件

- 用户报「报错了 / 慢 / 崩 / 不对 / 有时好有时坏」，且还不知道是哪一层的问题
- 修过一次又复发，怀疑没打到根因
- 需要在两个已知状态之间做回归定位（`git bisect`）

不触发：已知是哪一类问题（直接走 `01-slow-sql` / `02-oom` / `03-cpu` / `04-ai-exception`）；新功能开发（走 `feature-dev`）；只是代码写得不好看（走 `code-review`）。

## 前置条件（硬门）

1. 有可运行的环境（能起 dev server / 能跑测试），否则只能拿到「无法复现」的结论，先修环境。
2. 有原始错误信息（stack trace / 状态码 / 日志行），不是二手转述的「它不工作了」。
3. 已知现象发生的时间与频率（必现 / 偶发 / 特定账号）。
4. 允许插桩（改代码加日志、跑临时脚本）；不允许插桩的场景要先说明，改为只读观测。

## Phase 0：tea 四层快速分诊（建 loop 前先过）

| 层 | 症状 | 先查 |
|---|---|---|
| 环境层 | AI 调用超时 + TLS 握手失败 | DNS / TCP / 容器内 `openssl s_client` 与宿主机对比 |
| 数据模型层 | 某记录 0 行 / 静默丢数据 | 实体构造是否漏 NOT NULL 字段；旁路 catch 是否把 insert 失败降级成 warn |
| 类型系统层 | 集成测试 500 | 路由回落路径对可能为 null 的枚举直接 `.name()` |
| 可观测性层 | 数据没落库但日志没报错 | 埋点 / 计量的 catch 是否吞掉落库失败 |

四层都排除不掉，再进 Phase 1。

## 模板 A：不知道根因（主模板）

````text
你是「一盏茶」项目的调试者。现象：{{现象一句话}}。
已知：{{错误信息原文 / 状态码 / 出现频率 / 触发条件}}。

## 铁律
没有一条能在这个 bug 上稳定变红的命令之前，不许提出根因假设。
先建 loop，再 theorize。禁止靠读代码猜。

## Phase 0 快速分诊（先排除，再深入）
环境层（网络/TLS）→ 数据模型层（NOT NULL / null 字段）→ 类型系统层（null 枚举 / 空指针）→
可观测性层（旁路 catch 静默降级）。逐层给「排除 / 命中」结论与依据。

## Phase 1 建 tight feedback loop（花最大力气）
按序试，第一个成功的就是 loop：
1. 失败测试（打在能碰到 bug 的 seam 上）
2. curl / HTTP 脚本打 dev server
3. CLI 带 fixture 跑，stdout 对 snapshot
4. Playwright 驱动 UI，断言 DOM / console / network
5. 重放捕获的真实请求
6. 最小复现脚本（一个函数调用就能触发）
7. property / fuzz（偶发问题跑 1000 组随机输入）
8. `git bisect run`（两个已知状态间的回归）
9. 新旧版本同输入 diff
10. 结构化的人点脚本（最后手段）

交付物：**一条命令** + 期望输出 + 当前实际输出 + 复现率（必现 / N%）。
偶发 bug 的目标不是「干净复现」，是把复现率拉到可调试（>50%）。

## Phase 2-6（loop 建好后按序）
2. minimize：删无关输入 / 中间件 / 配置，直到最小可复现集
3. 3-5 个可证伪假设：每个假设写「如果成立，则 X 命令会看到 Y」；不许写无法验证的假设
4. 插桩验证：一次只验证一个假设；先看已有日志 / metrics，不够再加日志（加完要能撤）
5. 修根因 + 回归：修的是根因不是症状；补一条能锁住该 bug 的测试
6. 清理：撤掉临时日志 / 临时脚本；记录「这次什么环境问题让 debug 变难、该加什么自动化检查」

## 输出格式
- 每一步给「做了什么 / 看到什么 / 因此排除或确认什么」
- 根因结论必须能回答：为什么现在才出现 / 为什么只在这些条件下出现
- 结尾给：根因 / 修法 / 回归证据 / 未覆盖项
- 没建起 loop 就如实说「loop 未建立」，并列出已尝试的 3 条路与失败原因，不许编根因
````

## 模板 B：偶发 / 间歇性

````text
现象偶发：{{现象}}，复现率约 {{N%}}，触发条件疑似 {{条件}}。
目标不是干净复现，是把复现率拉高到可调试：
1. 写一个循环触发脚本（跑 100 次 / 并行 8 路 / 缩窄时序窗口）
2. 记录每次失败的输入、时序、线程/请求 id
3. 统计失败样本的共性（同一账号 / 同一时段 / 同一数据规模）
4. 拿到共性后，构造确定性复现（pin 时间、固定 seed、冻结网络）
输出：复现率提升曲线 + 共性结论 + 确定性复现命令。
````

## 检查清单

- [ ] 提示词要求先交付「一条命令」，不是先要根因
- [ ] Phase 0 四层分诊写进去了（tea 项目历史 bug 集中在这四层）
- [ ] 要求假设可证伪（写清「看到什么就算成立」）
- [ ] 要求一次只验一个假设，避免多变量同时改
- [ ] 要求修根因 + 补锁定测试，禁止只改症状
- [ ] 要求清理临时插桩，避免日志/脚本残留进提交
- [ ] 建不起 loop 时允许说「未建立」，但必须列已试路径与失败原因
