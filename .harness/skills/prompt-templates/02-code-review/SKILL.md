# 代码审查提示词（code-review）

审查场景的可复制提示词。**本技能只产出提示词，不做审查本身**；审查口径对齐 `.harness/skills/main-dev/expert-reviewer`（六维、四级、🟡 清零才过）。

## 触发条件

- 用户要审查一段 diff / 一个 PR / 一个新写的组件或接口
- 想让不同模型对同一份改动做交叉审查（同一提示词跑两遍）
- 合并前要一份「阻断项清单」，而不是「总体感觉不错」

不触发：让模型直接改代码（走 `feature-dev`）；定位线上故障（走 `debug-issue`）；只问某一行在干什么（直接问）。

## 前置条件（硬门）

1. 审查对象可取得：diff（`git diff` / PR 链接）或文件清单，**不能只给一句「看看我这段代码」**。
2. 已知本次改动的意图（要解决什么）；没有意图就无法判断「改得对不对」，只能判断「写得像不像」。
3. 已知改动级别（L1 UI / L2 逻辑 / L3 架构），决定审查深度与是否要求 ADR。
4. 审查者能读仓库（能打开 `AGENTS.md` / `DESIGN_SPEC.md` / `.harness/rules/编码规范.md` 核对依据）。

## 六维审查口径（写进提示词，不许模型自创维度）

| 维度 | 问什么 | 常见命中 |
|---|---|---|
| 正确性 | 边界、空值、并发、错误路径是否走通 | 数组下标未判空、`await` 漏掉、异常被 catch 吞掉 |
| 性能 | 有无 N+1、重复计算、无界集合、逐帧 setState | 循环里发请求、computed 里建大对象 |
| 安全 | 越权、注入、密钥、输入校验 | 前端直连第三方 AI、日志打 token、SQL 拼接 |
| 一致性 | 与项目现有模式是否一致 | 另起一套命名 / 目录 / 错误码 |
| 可维护性 | 命名、职责、注释、重复 | 一个函数干三件事、复制粘贴三段 |
| 架构合规 | 分层、依赖方向、红线 | views 直接写 IndexedDB、Controller 写业务逻辑 |

## 分级（必须标，不带级别等于没审）

- 🔴 **阻断**：会出错 / 越权 / 数据损坏 → 必须改，改完才能合并
- 🟡 **应改**：本次不改会留下维护债或触发红线 → **清零才过**
- 🟢 **建议**：更好但可选，作者可拒
- 🔵 **提问**：看不懂意图，请作者解释（不是缺陷）

## 模板 A：diff / PR 审查

````text
你是「一盏茶」项目的代码审查者。只审查，不改代码。

## 审查对象
- 改动范围：{{git diff 命令 或 PR 链接 或 文件清单}}
- 改动意图：{{要解决什么问题}}
- 改动级别：{{L1 UI / L2 逻辑 / L3 架构}}

## 依据（先读，再判）
- AGENTS.md（不可妥协 / 改动纪律 / 前端规范）
- DESIGN_SPEC.md（色令牌、圆角档位、触控 ≥44px、组件规则）
- .harness/rules/编码规范.md（15 条红线）

## 审查维度（六个都过，不许只挑一个说）
1. 正确性：边界 / 空值 / 并发 / 错误路径
2. 性能：N+1、重复计算、无界集合、逐帧更新
3. 安全：越权、注入、密钥外泄、输入校验
4. 一致性：是否复用项目现有模式（命名 / 目录 / 错误码 / 令牌）
5. 可维护性：命名、单一职责、重复、注释是否解释「为什么」
6. 架构合规：分层与依赖方向、红线命中

## 输出格式（严格）
每条发现一行，格式：
`[级别] 文件:行 — 问题 — 修法（可直接改的那种）`
级别：🔴 阻断 / 🟡 应改 / 🟢 建议 / 🔵 提问

示例：
`[🔴] src/views/BrewView.vue:142 — 组件直接 new WebGLRenderer，绕过 TresJS 生命周期 — 改用 <TresCanvas> + 组件树（3D_SPEC §六-1）`

## 硬规则
- 只说能定位到文件:行的问题；泛泛而谈（「建议加强类型」）不算发现
- 每条必须给依据（规则条款 / 设计令牌 / 现有同类实现），没有依据就降级为 🔵 提问
- 不评判作者风格偏好；项目有约定就按约定判
- 结尾给结论：`通过 / 有条件通过（🟡 N 条待清）/ 驳回（🔴 N 条）`
- 不重复说「整体不错」这类评价，只给发现与结论
````

## 模板 B：只审单个新文件

````text
审查 {{文件路径}}，按六维（正确性 / 性能 / 安全 / 一致性 / 可维护性 / 架构合规）。
对照 DESIGN_SPEC 与同类现有实现 {{参考文件}}。
输出：一行一发现（[级别] 文件:行 — 问题 — 修法），最后给「通过 / 有条件通过 / 驳回」。
没有发现就明确说「未发现阻断项」，不要凑数。
````

## 检查清单

- [ ] 提示词里带了具体 diff 命令或文件清单，不是「我的代码」
- [ ] 六维齐全，未增未减（增维度会让模型漏掉一致性）
- [ ] 分级规则明确，且写明 🟡 清零才过
- [ ] 要求「一行一发现 + 文件:行 + 修法」，防止长篇散文
- [ ] 要求每条带依据，防止主观口味当缺陷
- [ ] 要求给结论（通过 / 有条件通过 / 驳回），防止审完没有裁决
