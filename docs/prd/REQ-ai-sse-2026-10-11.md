# REQ-ai-sse-2026-10-11：SSE 流式输出立项建议书

> 来源：AI 工程化课程可吸收项（`docs/HANDOFF-2026-10-11-ai-course-execution.md` §6 ①）。
> 定位：**立项建议 + 需求分析初稿**，供用户一句话拍板。若立项，按 request-analysis + plan-control（Controlled 轨道）完整走流程。
> 现状复核（2026-10-11 实测）：tea 前后端**无 SSE**——后端无 `SseEmitter`/`Flux`，前端 `teaAI.ts` 无 `getReader`/流式消费（全仓仅 MCP 测试有一处 `Accept: text/event-stream`，非流式输出）。

## 1. 一句话结论（建议）

**建议暂缓立项（P2）**，理由见 §2 四维甄别第 4 维：当前五专家回复被 prompt 约束为 ≤200 字，流式对短文本的体验增益有限（感知上仅快 1~2 秒）；且 Phase 3 评测基线 + Q1 真实用户试用尚未完成，缺「用户真的嫌慢」的证据。立项收益在评测达标、试用反馈后再评估更划算。

## 2. 四维甄别（新功能立项先过，AGENTS.md §2 / REQ-quality-backlog §1.3）

| 维度 | 评估 | 得分 |
|---|---|---|
| 自由（团队自己会用） | 会：品鉴点评、茶路建议属长文本场景，自己用会想要打字机 | 1 |
| 用户 | 弱：无用户反馈「回复太慢」；Q1 试用未做 | 0.5 |
| 竞品 | 强：主流 AI 产品（ChatGPT/豆包等）默认流式，无流式显落后 | 1 |
| 伪需求风险 | **高**：prompt 规则 4 限 ≤200 字（Taster/Mentor/Brewer 等）；200 字流式增益 ≈ 首 token 提前 1~2s，不构成「必须做」 | **0.5** |

**合计 3/4（自由+竞品+半用户）——勉强过线但伪需求风险显著**。RAG 知识注入（Phase 2）后 librarian 回复变长（带来源引用），是流式唯一强场景；建议若立项，范围限定 librarian/advisor，不做全专家。

## 3. 需求分析初稿（若立项才生效）

### 3.1 功能点（F 编号）

| 编号 | 功能点 | 优先级 |
|---|---|---|
| F-1 | 后端新增流式端点 `POST /api/v1/ai/chat/stream`（SseEmitter 每事件推送，`data: [DONE]` 结束，Spring AI 原生支持） | P1 |
| F-2 | 前端 `teaAI.ts` 加流式分支（fetch + `getReader` + 逐事件渲染打字机；SSE 不可用时回退现有整段请求） | P1 |
| F-3 | 计量/配额/限流兼容：流式完成时结算 tokens（`AiUsageLogger` + `TraceRecorder` 沿用，不新建） | P1 |
| F-4 | 承重墙回归：非流式路径与 502 降级链完全保留，流式失败自动回退整段 | P0（约束） |

### 3.2 验收标准（Given-When-Then）

- **F-1**：Given 专家路径提问，When 调用 `/api/v1/ai/chat/stream`，Then 返回 `text/event-stream` 且末事件为 `data: [DONE]`；无 key 时返回 502（与整段一致）。
- **F-2**：Given 前端开启流式，When 收到首个事件，Then 页面立即渲染首段（不再等整段完成）；When 流中断，Then 自动回退整段请求并提示。
- **F-3**：Given 一次流式调用，When 流结束，Then `ai_usage_logs`/`ai_eval_traces` 各落一条且 tokens/latency 非空（防 TraceRecorder 静默丢数据重演，PR #43 教训）。
- **F-4**：Given 流式端点故障，When 用户提问，Then 前端走既有整段路径，评测集 50 条不回归（跑 `--judge` 子集）。

### 3.3 边界（本次不做）

- 不做多专家并行流（一次只流一个专家）。
- 不做中断续传/断点重连（浏览器 Tab 关闭即弃）。
- 不做流式进度百分比/剩余时间等 UI 附加态（保持最小改动）。
- 不改评测器（`eval-tea-ai.cjs` 继续走整段，避免评测口径分裂）。

### 3.4 影响分析

- **承重墙**：`src/services/teaAI.ts`（AGENTS.md §3 明令禁浏览器直连第三方 AI、降级链是承重墙）——F-2 改动必须保留降级，回归锁单测必须过。
- **后端**：`AiChatController` 增端点；`AiChatService` 增流式方法（复用五专家 agent 的 `callLlm`，仅响应方式变化）；Trace/计量结算时机从「整段返回后」改为「流结束事件」。
- **部署**：无新依赖（Spring AI 原生 SseEmitter）；无表变更；无迁移。
- **评测**：评测集不因流式改动；新增 1 条 F-2 前端回归（可 mock 流）。

## 4. 取舍与风险

| 取舍 | 建议 | 理由 |
|---|---|---|
| 全专家 vs 仅 librarian/advisor | **仅 librarian/advisor 先行** | 长文本场景集中；200 字约束下其余专家收益低 |
| SseEmitter vs WebFlux Flux | SseEmitter（MVC 现栈） | 不引入 WebFlux，改动最小 |
| 前端 fetch 流 vs EventSource | fetch + getReader | 可带 Authorization 头（登录用户），EventSource 不能带自定义头 |
| 流式失败处理 | 回退整段 | 承重墙语义：失败不降级用户到空白 |

**风险**：① 限流（10/min）与流式长连接叠加——建议流式也按一次调用计数，不放大配额；② 评测口径分裂——F-2 上线后重跑 `eval-tea-ai.cjs` 确认整段路径分不回归。

## 5. Not Doing（暂缓理由汇总）

- 当前评测 v3 基线（0.81）未到「优化体验」阶段——先做 Phase 3/4（能力正确性），再做体验层。
- 无用户慢反馈证据（Q1 未跑）——伪需求风险未排除前不动承重墙。
- 课程方案照搬（`data: [DONE]` 结算细节需按 tea 的 AiChatVo/Trace 对齐，不照抄）。

## 6. 决策点（用户拍板）

> **Q-SSE-1**：SSE 立项？推荐**暂缓（P2）**——等 Phase 3 评测 + Q1 用户试用后再评估；若你确认现在做，按本建议书走 request-analysis 立项，范围限 librarian/advisor。
