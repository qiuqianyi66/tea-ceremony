## 1. 产品定位与核心价值

**一句话**：一盏茶是沉浸式在线茶道 PWA——不是泡茶工具，是一座数字茶室。

- 业务闭环：入席 → 选茶 → 备器 → 煮水 → 冲泡 → 品鉴记录 → 个人成长
- 核心价值主张：**把 AI 从"套壳聊天"重构为"茶道专家团队"**——5 个有分工、会协作、知识可溯源的 AI 专家
- 差异化记忆点（简历层面）：3D 沉浸式茶室 + 多智能体专家团队 + 可解释评分 + 离线优先。面试官面过 100 个电商项目，不会见过这个

**核心结论：**

1. **方向完全命中**：Agent 是绝对核心（444 次），一盏茶多智能体方向是数据证明的最优选择，无需转向
2. **Java 路径成立**：实习岗明确存在"Java + Spring + SpringCloud + MyBatis + MySQL + Redis"的 Agent 开发岗，与一盏茶技术栈几乎一致；语言不换 Go
3. **高薪 Agent 岗标配**：Agent 编排 + Memory + RAG + LLM——一盏茶深度点全部覆盖，这正是要做透的部分
4. **框架不降级**：用 SAA 而非 Dify/Coze，面试时能讲底层编排而非拖拽配置

**决策修正（相对 ADR-011）**：原决策"不引入 Redis"。基于 AI 方向词频（Redis 47 次）+ 4 个真实使用场景，建议**引入 Redis**。这是工程决策变更，应更新 ADR-011 或新增 ADR-012，不在本文静默覆盖。

**差异化亮点：Agent 评测体系**——市场存在"Agent 大模型评测/Benchmark"方向（50-80K 岗）。一盏茶可将"八维可解释评分模型 + RAG 检索质量评测（问题集命中率）"包装为 **Agent 评测能力**，把"做产品"延伸到"评 Agent"，是同类简历少有的差异化。

## 5. 垂直深度设计（核心章节）

### 5.1 多智能体编排

**5 个专家 Agent 职责、工具与输出：**

| Agent | 职责 | 可调用工具 | 输出 |
|---|---|---|---|
| RecommendAgent 荐茶师 | 画像+场景 → 荐茶 | queryTeaCatalog、getUserProfile | 茶名+理由+冲泡参数+茶诗（结构化） |
| TastingAgent 品鉴师 | 八维评分+工艺 → 茶记 | getTastingBenchmark | 洞察性茶记、评分解读、改进建议 |
| CultureAgent 文化学者 | 文化问答（RAG） | retrieveKnowledge（向量检索） | 带出处的回答 |
| BrewCoach 冲泡教练 | 冲泡参数指导 | queryProcess、queryWare | 水温/时间/手法 |
| GrowthMentor 成长导师 | 周期复盘（Supervisor） | aggregateRecords、delegate | 阶段总结与建议 |

**编排模式（三种，按场景选用）：**
- **Routing 意图路由**：AI 入口先做意图识别 → 分派对应专家（荐茶/问答/指导直连）
- **Supervisor 监督编排**：复盘场景由 GrowthMentor 作为主管，按需委派 TastingAgent/RecommendAgent 并汇总
- **Graph 状态图**：节点 = 专家/工具调用，边 = 状态流转，支持条件分支（RAG 无命中 → 拒答分支；工具失败 → 降级分支）

**记忆两层：**
- 短期：会话上下文（多轮对话，TTL 控制）
- 长期：用户画像沉淀（偏好茶类/水温/香型/常用茶器），驱动个性化

### 5.2 RAG 工程（文化知识检索）

- **切片**：文化文档按语义切片（约 500 字/片，重叠 50 字），保留章节元数据（标题/分类/来源）
- **嵌入**：`text-embedding-v3`（1024 维）写入 pgvector，建 hnsw/ivfflat 索引
- **检索**：向量 top-k（k=5）+ 元数据过滤，必要时 rerank
- **生成**：检索片段注入 prompt，**强制引用格式 `[来源:标题]`**
- **防幻觉**：无命中 → 明确告知"无法从知识库回答"，不编造；低置信度 → 主动说明
- **评测**：建问题集（问题 → 期望文档），检索命中率纳入冒烟测试

### 5.3 可解释评分模型（后端重写同口径，拒绝黑盒）

- **八维（1-5 分）**：苦涩度（反向）、甜度、回甘、醇厚度、香气持久度、茶韵、叶底、心境
- **工艺系数（0-1，可分解）**：
  - 温度因子 = `max(0, 1 - |实际水温-最佳水温|/30)`
  - 时间因子 = `max(0, 1 - |实际时间-最佳时间|/(0.5×最佳时间))`
  - 基础系数 = 温度/时间两因子平均
  - 茶器补偿 + 水质因子 → 最终系数
- **综合评分** = `(8 维平均，苦涩度用 6-苦涩度转适口度) × 2 × 工艺系数`，clamp 到 1-10
- 每个因子都可在 UI 展示"为什么是这个分数"
- **延伸为 Agent 评测体系（标注：简历差异化延伸，非产品核心）**：① 输出质量评测——评分模型对 Agent 生成的品鉴/复盘结果做可量化打分；② 检索质量评测——RAG 问题集命中率（问题 → 期望文档）。对应市场"Agent 评测"高薪方向（50-80K 岗），但这是**加分项不是必需项**，排在 M6+ 可选，不阻塞主链路

### 5.4 离线优先与幂等同步

- 前端 IndexedDB 记录带 `sync_status`（pending/synced/failed）
- 提交时带 `client_id`（客户端 UUID），服务端加唯一约束 → **重放/重网不产生重复记录**
- 联网后批量同步，失败重试；冲突以服务端为准；写入前 `toRaw` 去代理（防 DataCloneError）

### 5.5 AI 工程治理

- **缓存两级**：Caffeine（L1 本地）+ Redis（L2 共享），文化数据/热点茶叶走 Spring Cache
- **语义缓存**：相似问题先做 embedding 匹配 Redis 缓存 → 命中直接返回，降低 LLM 成本
- **限流**：Redis 滑动窗口（用户级 + 全局）——**诚实标注**：单实例下内存滑动窗口已够用，用 Redis 的主因是 JD 技能覆盖 + 为多实例扩展预留；如实定位，不吹"分布式高并发"
- **JWT 黑名单**：登出时将 token 写入 Redis（带 TTL），无状态方案下实现登出失效
- **用量计量**：`ai_usage_logs` 记录 agent/model/prompt_tokens/completion_tokens/cost/latency；每日预算统计 + 阈值告警
- **Prompt 版本管理**：`agent_prompts` 表（agent/version/content/状态），支持灰度与回滚
- **流式**：SSE 推送，可中断
- **降级链（承重墙，必须保留并回归）**：LLM 失败 → 熔断 → 规则引擎回复 → 前端离线兜底

## 8. 非目标（明确不做）

- 不重写前端（保留 Vue 3.5 现有代码与设计系统）
- 不迁移历史用户数据（新库重新初始化，全新部署）
- 不做移动端原生 App（维持 PWA）
- 不做微服务拆分（单体足够，架构隔离 AI 层即可）
- 不引入消息队列（Spring Event 足够）
- 不编造茶文化数据（迁移现有 `src/data/` 与 `backend/seeds/`，不确定标"待核实"；数据扩充为后续增强）
- 阶段六（简历功能）用户明确不做

## 9. 验收标准（整体 Done 定义）

1. M0-M7 全部 Gate 达成，每阶段 Gate 留痕
2. 前端 `npm run quality` 保持绿，后端测试覆盖率 ≥ 70%（核心业务 + AI 降级路径 100%）
3. 完整演示链路：注册 → 选茶 → 冲泡 → 品鉴 → AI 茶记 → AI 复盘 → 个性化荐茶
4. 四个深度点均有对应代码与测试：多智能体编排、RAG 带出处、可解释评分、幂等同步
5. 部署文档可让任何人从零复现（含 Redis / pgvector）
6. 开源仓库整洁：README / LICENSE / ADR / CHANGELOG / CONTRIBUTING 齐备
