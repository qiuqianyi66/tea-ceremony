# REQ：AI 项目化改造需求分析（按 Leo 方法论）2026-10-09

## 0. 结论先行

- 参照物：Leo《零 AI 产品经验，如何拿到 AI 产品 offer》（x.com/double_burger_2/status/2106653589804597492）。
- 核心判断：**tea 的 Agent 能力已超文章基准（五专家 + RAG + 工具 + 记忆 + 降级），真正缺的是「评测体系」**——文章反复强调"评测是绕不开的能力、最能拉开差距"（5 条 JD 4 条写评测，薪资最高那条全是评测）。
- 改造重头 = **给 AI 茶灵建一套完整评测体系**（评测集 + 四层归因 + 考点加权 + 程序化校验 + LLM-as-Judge + pass^k + 效率成本），产出**真实迭代数字**写进简历。
- 明确不做：多 agent 接力流水线（H9 已砍）、模型训练、引入 promptfoo/DeepEval 依赖（自建最小评测，借鉴其设计）。

## 1. 文章方法论提炼（改造依据）

### 1.1 AI 产品岗三层要求（JD 拆解结论）

| 层 | 要求 | tea 现状 |
|---|---|---|
| 产品基本功 | 需求调研/PRD/竞品/原型/数据分析 | 已有（PRD 文档体系 + ai_usage_logs 数据） |
| AI 特有 | 懂概念/懂原理/会评测/能做 Demo | 概念原理可讲清（五专家/RAG/工具/MCP）；**评测缺**；Demo 已能跑 |
| 加分项 | 上线过/真实用户/懂场景 | PWA 可部署；场景极具体（茶道）✓ |

### 1.2 项目五步法（文章第三节"跟练"）

1. 想清楚"为什么"（服务谁/现状痛点/为什么是 Agent）
2. 设计能力与范式（工具/范式/记忆/边界）
3. 搭建
4. **做评测并基于评测迭代（拉开差距的一步）**
5. 让真实用户用起来

### 1.3 评测方法论（文章第四节，改造核心）

- **不只看结果，记录完整 Trace**（防"静默失败"：结果对但过程错，如没调工具靠编）。
- **四类指标不揉总分**：①结果质量（主门槛）②过程质量（诊断）③效率成本（优化）④安全稳定（硬门槛）。顺序：先安全 → 再结果 → 最后过程效率。
- **四层归因**：输入层/上下文层/规划层/执行层——每个失败定位到"第一个出错的节点"，评测报告 = 研发待办清单。
- **考点法**：需求拆考点（否决型/核心型/一般型 + 权重），任务得分 = Σ(考点×权重)/Σ权重；否决型 0 分直接判 0。
- **pass^k**：同一测试样本独立跑 k 次，k 次全过才算通过（一次成功不算数）。
- **LLM-as-Judge**：每维单独评、做选择题（0/1）、给"无法判断"选项、人工校准一致率、防位置偏差、多采样、持续人工抽检。
- **效率成本从第一版就记**：用户等多久（首字/完整）、花多少 token。

## 3. 改造范围

### F-A 评测体系（重头，文章第四节全量落地）

| # | 任务 | Given-When-Then 验收 |
|---|---|---|
| F-A1 | 构建 AI 茶灵评测集（docs/ai-eval/cases/，YAML，借鉴 promptfoo 结构） | Given 五专家与六类任务；When 编写典型/边界/对抗样本 ≥40 条（每专家 ≥8）；Then 每条含 input/expected/考点/权重/否决标记，可被评测器读取 |
| F-A2 | Trace 记录（ai_eval_traces 表 + AiChatService 埋点） | Given 一次 AI 对话；When 完成一轮；Then 记录输入/上下文快照/路由决策/工具调用及结果/输出/耗时/token/异常，四层字段齐全 |
| F-A3 | 考点法评分器（node scripts/eval-tea-ai.cjs） | Given 评测集 + 运行结果；When 按考点打分；Then 输出否决型 0 分直接判 0，否则 Σ(考点×权重)/Σ权重，单条与汇总分可解释 |
| F-A4 | 程序化校验 | Given 可规则判分的考点（茶类归属/温度区间/冲泡时长/降级触发/RAG 命中/工具参数）；When 自动运行；Then 无需 LLM 判定即得 0/1 |
| F-A5 | LLM-as-Judge（单维评委 Prompt + 校准脚本） | Given 同一批样本人工已标注；When 机评跑完；Then 每维独立评委、0/1 选择题、含"无法判断"选项；一致率达到阈值（建议 ≥85%）才视为可用 |
| F-A6 | pass^k 稳定性运行 | Given 评测集子集（≥10 条）；When 每条独立跑 k=3 次；Then k 次全过记通过，输出 pass^3 指标 |
| F-A7 | 效率成本报告（ai_usage_logs 消费端 + 延迟埋点） | Given 一轮 AI 调用；When 统计；Then 输出首字延迟/完整延迟/输入输出 token/成本估算，四类指标报告含效率成本维 |
| F-A8 | 安全稳定维度 | Given 对抗样本（越权/危险指令/降级场景）；When 运行；Then 输出降级触发率、有害输出拦截率，作为硬门槛前置展示 |
| F-A9 | 迭代记录（docs/ai-eval/ITERATIONS.md） | Given 每版改造；When 完成评测；Then 记录版本/改动/四维指标变化/归因失败案例，形成可写简历的迭代史 |

## 4. 不做什么（Not Doing）

- **不做多 agent 接力流水线**（H9 判砍延续）：tea 维持单请求单专家路由，不引入 MetaGPT 式角色接力。
- **不做模型训练/SFT/RL**：文章要求"了解原理"即可，训练数据长什么样能讲清（可出一页概念文档，不实际训练）。
- **不引入 promptfoo/DeepEval 依赖**：自建最小评测器，仅借鉴设计（避免新增依赖 + 与 Spring Boot/TS 栈异构）。
- **不改前端主流程**：F-B3 报告页是可选项，核心评测全在后端 + 脚本。
- **不做真实用户拉新运营**（可选项，见决策 D-A4）。

## 5. 影响分析

| 项 | 影响面 | 风险与缓解 |
|---|---|---|
| Trace 埋点 | AiChatService + 新表 | 表走 Flyway 迁移（.harness/skills/biz-dev/09-db-migration）；埋点只读不改变行为；不影响降级承重墙 |
| 评测器 | 新脚本（node） | 独立脚本，不挂 CI（要 AI key，见 D-A2）；本地/手动运行 |
| LLM-as-Judge 调用 | 费用 | 用小模型（如 qwen-turbo）做 judge + 评测集 ≤50 条，单轮成本可控（用户偏好红线：不浪费 token 额度） |
| 长期记忆（若做） | 用户隐私 | 读写接口 + 可查看删除 + 不存敏感信息（隐私红线） |
| 运行时 Skill（若做） | PromptService | 版本化登记，回滚安全 |
| 简历素材 | 无 | 真实数字才写，跑不出来不编（文章明确：数字必须真实跑出来的） |

## 6. 优先级与决策

建议顺序：**F-A1（评测集）→ F-A2/A3/A4（骨架+程序化）→ F-A5/F-A6（机评+稳定性）→ F-A7/A8（效率安全）→ F-A9（迭代记录）→ F-C1（简历）**；F-B 系列按 D-A3 决定是否并入。

| 决策 | 问题 | 建议 |
|---|---|---|
| D-A1 | 评测集规模与来源 | 初始 40-50 条人工编写（覆盖典型/边界/对抗），后续从真实日志提取补充；每专家 ≥8 条 |
| D-A2 | Judge 模型选择与运行方式 | 用现有 DashScope key 的小模型（qwen-turbo）做 judge；评测脚本手动/定时运行，不挂 CI（避免每次 PR 烧钱） |
| D-A3 | F-B 系列（运行时 Skill / 长期记忆）本轮是否做 | 建议本轮只做 F-B1（Skill 第一版，成本低故事好讲）；长期记忆（F-B2）排下一轮 |
| D-A4 | 是否拉真实用户试用（文章第五步） | 可选：部署 PWA 发同学群收集反馈，反馈进评测集；成本低收益高，建议做 |
