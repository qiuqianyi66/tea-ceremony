# 数据治理规范（DATA_POLICY）

> 覆盖 `src/data/` 全部茶文化数据集（茶 / 茶人 / 节气 / 产区 / 工艺 / 茶器）。
> 目的：防止编造、防数据漂移、保证任何一条数据都能追溯到来源。
> 配套规则：AGENTS.md §8 数据规范、`tea-tasting` 基准表、`docs/ADR/`。

## 0. 铁律

1. **不编造。** 茶名、茶器、历史人物、引文、产地、工艺参数必须有据可查；不确定标 `"待核实"`，禁止编一个"看起来对"的值。
2. **映射防御。** 跨数据集引用（产区名茶 → 茶库、节气推荐 → 茶类）必须精确匹配或显式 `undefined`，禁止模糊猜测（参照 `findTeaByName` 的精确匹配 + 回归测试模式）。
3. **来源可追溯。** 每类数据必须能回答"这条数据从哪来、核过没有、什么时候核的"。

## 1. 新增数据硬性规范

**新增或新增字段的任何数据集，每条记录必须包含：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `string` | 稳定业务 ID（小写蛇形，如 `longjing`），禁止用序号或中文名做 ID |
| `source` | `string \| string[]` | 来源（文献名 / 机构名 / 官方名录），可溯源 |
| `verified` | `boolean` | 是否已核对来源原文；`false` 表示待核，界面应展示"待核实" |
| `updated_at` | `string` | `YYYY-MM-DD`，本次核对/修改日期 |

**示例（新增茶款）：**

```ts
{
  id: 'huangshanmaofeng',
  name: '黄山毛峰',
  origin: '安徽黄山',
  source: ['《中国名茶志》', '国家地理标志产品名录'],
  verified: true,
  updated_at: '2026-10-01',
  // ...其余业务字段
}
```

**校验门槛**：新增数据集必须配类型定义（`interface`）+ 至少一条字段完整性单测（断言每条记录 `id/source/verified/updated_at` 非空，参照 `solarTerms.spec.ts` 的"茶类词 ∈ 枚举"断言模式）。

## 2. 存量数据盘点（2026-10-01）

存量数据**不加字段、不批量改写**（避免无意义大 diff），来源职责由文件头注释承担；本表是权威口径。

| 数据集 | 文件 | 条目 | id | source 标注方式 | verified 状态 | 备注 |
|---|---|---|---|---|---|---|
| 茶 | `src/data/teas.ts` | 40+ | ✅ | ❌ 无标注（story 史载，无字段） | 未标注 | 数据量最大，priority 最高 |
| 茶人 | `src/data/teaMasters.ts` | 21 | ✅ | 文件头注释（《茶经》《大观茶论》等） | 注释声明"当前无待核实" | quote 为原典原文 |
| 节气 | `src/data/solarTerms.ts` | 24 | ✅ | 文件头注释（全唐诗/宋诗，诗人归属抽查核对） | 抽查级 | 节气日期为公历约期（±1 天） |
| 产区 | `src/data/tea-regions.ts` | 52 | ✅（province 名） | 文件头注释（中茶协 / 省农业农村厅 / 地理标志名录） | 未逐条标注 | province 必须与 china-map.json 完全匹配 |
| 工艺 | `src/data/teaProcesses.ts` | 6 茶类 | ✅（teaType） | ❌ 无标注 | 未标注 | 参数基于行业常识，需补 source |
| 茶器 | `src/data/teawares.ts` | 10+ | ✅ | 文件头"基于真实茶道资料"+ story 引文献 | 未逐条标注 | story 引文须核实原文 |

**存量维护规则**：改动存量记录时，在文件头注释补一句来源出处；新增记录按 §1 硬性规范执行。禁止为了"看起来合规"给存量数据批量塞 `verified: true`（那是编造核实状态）。

## 3. 数据质量分级

| 级别 | 含义 | 处理 |
|---|---|---|
| 已核实 | 引文/事实对照过原文或官方名录 | 可正常展示 |
| 待核实 | 有来源但未逐条核对，或来源单一 | 界面标注"待核实"；茶文化展示禁止把待核实当事实叙述 |
| 无来源 | 无法溯源 | 禁止入库；必须找到来源或删除 |

## 4. 治理流程（改动茶文化数据时）

1. 先读目标文件 + 对应类型定义 + 相关 spec（防漂移）。
2. 新增/改动记录 → 标注 `source`（可只写文件头注释）+ 核对引文。
3. 跑相关单测（`npm run test`），涉及映射的确认回归测试仍绿。
4. 动了字段结构（类型变化）→ 属 L3 改动，先写 ADR 再动。
