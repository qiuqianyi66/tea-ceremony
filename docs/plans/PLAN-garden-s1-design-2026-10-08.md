# 茶园 S1 切片实施方案（PLAN · 已确认）

## 1. 结论先行

- S1 = 落地契约 `POST/GET /api/v1/garden-plants` + 新增能量账本（品鉴落库自动产能量）+ 一键收集 + 阶段推进映射 3D。
- 数据：新增 `garden_energy_events` 表（Flyway V4），`garden_plants` 扩展 `energy` 列、`status` 语义化为阶段。
- 触发：后端 `TastingRecordService.create` 同事务记账，幂等键复用 `user_id + client_id`（品鉴记录 client_id），天然防重。
- 配置：能量规则与阶段阈值放 `application.yml`（配置化，重启生效），S1 不建配置表。
- 级别：L3（新表 + 迁移 + 新接口），走 ADR-015 + Flyway upgrade/downgrade 往返。

## 2. 范围

### 做（S1）

| 块 | 内容 | 来源 |
|---|---|---|
| 账本 | `garden_energy_events` append-only，幂等 `user_id + client_id` | PRD F-G6 |
| 产能量 | 品鉴记录落库自动记账：每次冲泡 +5、笔记每 100 字 +10（配置化） | PRD F-G1 |
| 收集 | 未收能量气泡（前端）+ 一键收集 → 累计到植物能量 | PRD F-G2 |
| 阶段 | 收集后按累计能量推进阶段：planted → growing → blooming → harvested；3D 映射 | PRD F-G2/G3 |
| 契约 | 落地既有 `POST/GET /api/garden-plants`（移除"⚠ 未实现"标注）+ 能量总览/收集端点 | api-contract.md |

### 不做（S1 边界）

- streak 连续奖励、排行、勋章、奖励解锁、称号、茶园装饰：S2/S3，不做。
- 游客能量落库：不做（游客模式不调 API，沿用 records 同步守卫）。
- 能量配置表 / JSONB 配置：S1 用 `application.yml`，S2/S3 上配置表。
- 后端不重算品鉴评分、不改品鉴落库链路、不动 3D 视觉本身（只接阶段映射）。

## 3. 数据层设计（V4__garden_energy.sql）

```sql
-- 1) garden_energy_events：能量事件账本（append-only，幂等 user_id + client_id）
CREATE TABLE garden_energy_events (
    id          INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id     INTEGER NOT NULL,
    client_id   VARCHAR(64) NOT NULL,
    amount      INTEGER NOT NULL,
    source      VARCHAR(30) NOT NULL,          -- tasting（S1 唯一来源；brew/streak/quest 预留）
    collected_at TIMESTAMP,                    -- NULL=未收；非空=已收集
    created_at  TIMESTAMP NOT NULL DEFAULT now()
);
COMMENT ON TABLE garden_energy_events IS '茶园能量事件账本（append-only，幂等 user_id+client_id，防通胀可审计）';
CREATE UNIQUE INDEX uk_garden_energy_events_user_client ON garden_energy_events (user_id, client_id);
ALTER TABLE garden_energy_events ADD CONSTRAINT fk_garden_energy_events_user_id
    FOREIGN KEY (user_id) REFERENCES users (id);

-- 2) garden_plants 扩展（V1 最小集回填：status 语义化为阶段 + 新增能量累计）
ALTER TABLE garden_plants ADD COLUMN energy INTEGER NOT NULL DEFAULT 0;
COMMENT ON COLUMN garden_plants.energy IS '已收集能量累计（浇灌用）';
-- status 语义：planted / growing / blooming / harvested；V1 存量行 'pending' 归并为 'planted'
UPDATE garden_plants SET status = 'planted' WHERE status = 'pending';
COMMENT ON COLUMN garden_plants.status IS '阶段：planted 种下 / growing 生长 / blooming 开花 / harvested 收获';
```

设计要点：

1. 一条品鉴记录 = 一条能量事件（amount = 5 + floor(len(notes)/100)*10，source=tasting）。不拆 tasting/brew 两条——幂等键唯一约束下拆两条会冲突，合并单事件满足最小实现。
2. 事件账本 append-only 不 UPDATE 金额；收集状态用 `collected_at` 标记，防通胀可审计（PRD F-G6）。
3. 阶段推进是**事件聚合的结果**：收集时累加未收事件金额到 `plants.energy`，按阈值表推进 `status`（只升不降），不直接改事件。

## 4. 接口设计（契约扩展，对齐新栈 /api/v1）

| 方法 | 路径 | 请求体 | 成功响应 | 错误 |
|---|---|---|---|---|
| POST | `/api/v1/garden-plants` | `GardenPlantCreate`（含 `client_id`） | `GardenPlantVo` 200（幂等 upsert） | 400/401 |
| GET | `/api/v1/garden-plants` | — | `list[GardenPlantVo]` | 401 |
| GET | `/api/v1/garden-energy` | — | `GardenEnergySummaryVo`（待收/已收/累计/阶段） | 401 |
| POST | `/api/v1/garden-energy/collect` | — | `GardenEnergySummaryVo`（收集后最新） | 401 |

`GardenPlantVo`：`id, client_id, plant_type, status, energy, created_at, updated_at`（snake_case）。
`GardenEnergySummaryVo`：`pending_amount`（未收）、`collected_amount`（已收）、`total_energy`（plants.energy 累计）、`phase`（当前阶段）、`phase_thresholds`（各阶段阈值，前端显示进度）。

- 幂等 upsert：同 `user_id + client_id` 已存在返回原记录（对照 record 域承重墙：查重 + 唯一索引兜底）。
- 归属：所有查询按 `user_id` 过滤。
- 契约路径 `/api/garden-plants` → `/api/v1/garden-plants`（新栈统一 v1，api-contract.md 同步更新，并移除"⚠ 未实现"标注）。

## 5. 能量生产触发（后端）

1. `TastingRecordService.create` 落库成功后，同事务调用 `GardenEnergyService.recordTasting(userId, clientId, notes)`。
2. 金额计算：`5 + floor(len(notes)/100) * 10`；规则来自配置 `garden.energy.rules`。
3. 幂等：能量事件 `client_id` 复用品鉴记录的 `client_id`；品鉴重复提交（幂等返回已有）不会写第二条能量事件；并发兜底 = 唯一索引 + DataIntegrityViolation 转幂等返回（对照 record 域）。
4. 依赖方向：`record.service → garden.service`（Service 层横向调用，不违反 Controller→Service→Repository 单向链）；ArchUnit 只查分层方向，跨域 service 调用需在实现后跑 LayerDependencyTest 确认。
5. 游客：前端游客不发起品鉴同步（records 同步守卫），后端无游客能量路径。

## 6. 收集与阶段推进（后端）

1. `collect`：同事务把该用户 `collected_at IS NULL` 的事件置为已收集，金额累加到 `plants.energy`。
2. 阶段推进：对照阈值配置 `garden.energy.phases`（例：planted 0 / growing 100 / blooming 300 / harvested 600，可调），`status` 升级到不高于累计能量的最高阶段，只升不降。
3. 无植物时（未 POST 种植）：能量先挂账（事件已记），收集后仍可推进；前端引导种植（POST upsert 默认 plant_type）。

## 7. 前端设计（GardenView + 3D 映射）

1. `src/services/api/garden.ts` 新增（对照 records.ts 模式）：`gardenApi.list/create` + `energyApi.summary/collect`，路径 `/v1/garden-plants`、`/v1/garden-energy`。
2. GardenView 地区页（有 regionId）：挂载时拉 `summary`；有 `pending_amount > 0` 显示"待收能量 +N"气泡（顶栏右侧，设计令牌），点击一键收集（POST collect），成功后更新阶段并触发 3D 阶段映射。
3. 3D 映射：后端 `status`（planted/growing/blooming/harvested）→ 前端 `PlantedTea.status` 视觉档位（sprout/seedling/growing/mature），`TeaGardenScene3D` 接 plants 数组渲染；不改 3D 视觉本身（3D_SPEC 约束）。
4. 游客：不显示能量 UI（沿用游客模式）。
5. 无能量历史：气泡隐藏，纯观赏不变（降级兼容）。

## 8. 配置（application.yml，新增段）

```yaml
garden:
  energy:
    rules:
      brew-base: 5          # 每次冲泡基础能量
      note-per-100: 10      # 笔记每 100 字能量
    phases:
      planted: 0
      growing: 100
      blooming: 300
      harvested: 600
```

## 9. ADR-015 要点（实现时落 docs/ADR/ADR-015.md）

- 决策：事件账本（append-only + collected_at 标记）而非直接改列；幂等复用品鉴 client_id；阶段事件驱动聚合；配置化先行 application.yml。
- 备选：直接改 plants.energy 列（无审计、难防通胀）→ 否；拆 tasting/brew 双事件（幂等键冲突）→ 否；配置表（S1 过重）→ S2 起。

## 11. 影响分析

- 新表 + 新接口：无破坏性变更；`/api/garden-plants` 契约路径改 v1，但旧端点从未实现（404），无兼容负担。
- 品鉴落库链路加能量记账：同事务，失败回滚不污染品鉴记录；幂等防重。
- 前端：GardenView 新增能量 UI，纯观赏降级保留（无能量时不变）。
- 承重墙检查：teaAI.ts 降级链、品鉴幂等承重墙、3D 视觉均不改动逻辑，仅新增调用。
