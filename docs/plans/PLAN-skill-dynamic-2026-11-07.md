## 二、根因（为什么做完前四批仍然「不到位」）

前三类失效（看不见 / 做不到 / 会过期）都能用正则、路径、名单算出来，但**算得出来 ≠ 跑得动**。当前所有结论都是「文件层面没问题」，缺一条「真实任务里技能真被选中、真被用对」的证据链：

1. 留痕 0 条 → `docs/reference/skill-layering.md` 的升降判据（「储备被真实点名 ≥3 次则升」「活跃连续 3 切片零调用则降」）**至今空转**。
2. 跨技能裸引用从未检测。实测已确认一例：`plan-control` 正文写「上游 grill-me-pro→brainstorming；下游 writing-plans→executing-plans→code-review-analyzer」，这 5 个技能 tea 全都没有。
3. 半可执行 10 个、自写纯文档 26 个从未逐个判「该不该沉」，只有一刀切的总数。

## 三、子问题与方案

### F10 跨技能引用死链检测（P1，只报不阻断）

`verify-harness` §4m 只查**反引号内的路径/命令**锚点；技能正文里裸写的「走 xxx」「下游 yyy」不在任何人的检查范围。

- 做法：建技能名集合；扫正文里形如 `[a-z][a-z0-9-]{2,}` 的 token，出现在「→ / 走 / 用 / 见 / 下游 / 上游」邻域、且不在集合内的标为可疑。
- 度量：可疑引用数 + 人工抽检 20 条算精确率。
- 先只报不阻断：裸 token 比对天然高误报（`sync_status`、`type-check` 都形似技能名）。

### F11 一条真实任务的端到端回归（P0）

前四批全部是「读文件 + 数正则」，一次真实执行都没跑过。

- 选 1 条低风险真实任务，强制走完整链路：读族 README 路由 → 读命中的 SKILL.md → 跑其「确定性入口」脚本 → 写切片 `summary.md` 的「调用技能」行 → 跑 `audit-skill-usage`。
- 产出：留痕从 **0 → ≥1**，升降判据首次有真实数据；同时验证 F3 的强制在真实流程里是否顺手（不顺手就改机制，而不是留着让人绕过）。
- 必须记录：选中了哪个技能、为什么选它、读了哪些资产、脚本真跑没跑、结果对不对。

### F12 半可执行 10 个逐个判定（P2）

名单（实测）：`javascript-node`(导入,8 步)、`shadcn`(导入,20)、`10-scheduled-task`(2)、`expert-reviewer`(2)、`request-analysis`(2)、`unit-test-ci`(9)、`02-code-review`(3)、`03-debug-issue`(7)、`04-performance`(6)、`00-bug-diagnose`(10)。

判据三条：① 命令跨环境一致（依赖 npx / 网络的 → 不沉淀）；② 需要人判断的 → 不沉淀；③ 步骤重复且已有一键入口的 → 直接指向现成脚本。

预期只有 2–3 个值得下沉（`unit-test-ci` 的 9 步其实等于 `npm run verify`；`00-bug-diagnose` 的 10 步可抽出取证脚本）。

### F13 自写 26 个纯文档二分类（P2）

分「流程型 / 格式型（无脚本合理，标 N/A）」与「本可机械检查、只是没写」。后者预期在 `06-exception-handling`（错响应格式）、`07-business-validation`（校验注解缺失）这类。

### F14 README 路由表逐名核对（P2）

AGENTS.md 铁律「README 不列 = 技能不存在」，但没人验过反向：README 列的名字是否真存在、目录是否都在 README 里。成本低，与 §4j 互补。

### 不做（已否决，勿重提）

- 导入层 41 条触发句补齐：改了下次同步上游即丢。
- 82 个纯文档硬接脚本：56 个导入包无对应脚本，硬接即编造。
- 给 109 个技能写 eval case：批次成本远超收益。
