# K13 + P1-2 设计（B 线，待确认）

## 1. 结论先行

- **K13 repo map**：`scripts/gen-repomap.cjs` 半自动生成仓库地图——纯 fs 起步（零新依赖），tree-sitter 二期演进。解决 AI 定位入口的上下文成本。
- **P1-2 复杂度路由**：Orchestrator 三档分级（SIMPLE / STANDARD / COMPLEX）——简单问答走廉价路径省 token，复杂分析走专家+慢模型保质量。显式 agent 优先与降级承重墙不变。
- 两者独立，可分别开工；设计确认后再实现。

## 2. K13 repo map（gen-repomap.cjs）

### Context

- AI 编码上下文是稀缺资源（AGENTS.md 三层语义红线）；仓库 60+ 技能、src/ + backend 双栈，AI 开工前定位入口靠读 AGENTS.md 索引 + 人肉探查。
- 现状：scripts/*.cjs 已有纯 fs 无依赖模式（verify-harness.cjs）；"手动地图可维护期延后"（PLAN-harness-optimization v2 K13 备注）。
- 目标：生成确定性、可复核的符号级仓库地图，AI 开工前一次读取即可定位入口与调用链。

### 方案

**阶段 1（纯 fs，零新依赖，本次实现）**

- 扫描 `src/` + `backend/src/main/java/`，按文件类型提取符号：
  - `.vue`：`<script setup lang="ts">` 内 export function/const、组件名（文件名）、props/emits 声明
  - `.ts`：export interface / type / function / const
  - `.java`：class / record / interface + 关键注解（@RestController/@Service/@Repository/@Entity + @RequestMapping 路径）
- 输出 `.harness/wiki/repo-map.md`（契约文件）：目录 → 文件 → 顶层符号 + 关键路径（Controller 路由 / Service 方法 / 实体表名）。
- 体积控制：只收顶层入口与公开符号，不展开方法体；单文件 ≤3 行。

**阶段 2（tree-sitter，二期，先不实现）**

- `web-tree-sitter` + typescript/java grammar 精确解析，处理嵌套泛型、模板字符串、条件编译。
- 输出 JSON 明细（供检索）+ Markdown 摘要（供上下文）。package.json 新增 devDependency（引入前查 package.json 与 license）。

### 验证

- L2：脚本实跑 EXIT=0；抽查符号命中（如 GardenController 路由、TastingRecordService.create）；输出不超阈值（地图 ≤ 300 行）。
- 不挂 CI 门禁（地图是上下文辅助，不是正确性门禁；挂门禁会把工具维护成本变成每次提交负担）。

### Trade-offs

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯 fs 正则（阶段 1） | 零依赖、快、可维护 | 嵌套/泛型解析差；vue 模板内逻辑漏收 |
| tree-sitter（阶段 2） | 语法精确 | 引入 3+ 依赖；维护成本 |

决策：先 fs 后 tree-sitter——先用最小成本拿到 80% 收益，精度不够再升级。

## 3. P1-2 Orchestrator 复杂度路由

### Context

- 现状（AgentOrchestrator.java 实读）：显式 agent → 校验枚举；无 agent → 文化关键词粗分 → LIBRARIAN；其余 → null（透明代理）。五专家全部接线（BaseExpertAgent），单一 DashScope 模型。
- 趋势：Model Router 复杂度分级省 token（-64% 量级）；当前简单文化问答与复杂多轮分析同模型同成本。

### 方案

**三档复杂度（规则分级，不做 per-query LLM 分级）**

| 档 | 判定信号 | 路径 |
|---|---|---|
| SIMPLE | 最后用户消息 ≤40 字 且 无深度动词 且 历史 ≤1 轮 | 文化域（LIBRARIAN）+ 廉价模型（`tea.ai.routing.model.simple`，可空=沿用默认） |
| STANDARD | 默认 | 现路径不变 |
| COMPLEX | ≥3 轮历史 / 消息 >200 字 / 含"推荐 分析 对比 为什么 方案 计划"等深度动词 | 专家 + 慢模型（`tea.ai.routing.model.complex`，可空=沿用默认） |

- 路由序：显式 agent > 文化关键词（LIBRARIAN）> 复杂度分档（仅影响模型选择，不影响 agent 判定）。
- 实现：`AgentOrchestrator.complexity(AiChatRequest, int historySize)` 纯函数 + application.yml `tea.ai.routing.*` 配置（@Value 注入，对齐 tea.jwt 模式）。
- 承重墙：降级链 502 → 前端规则回复不变；配置模型名不可用/为空 → 回退默认模型；AgentType 契约零改动；`AiChatService.dispatch` 只新增模型选择参数。

### 验证

- L2：AgentOrchestratorTest 增复杂度用例（三档边界：39/40 字、1/3 轮、动词命中）；AiChatServiceTest 回归；`mvn test` 全量绿。
- 不做端到端成本测量（无真实多模型 key 前，先验证路由判定正确性）。

### Open Questions

- **Q1** 是否引入第二模型（不同档位不同模型名）？建议：先不引入——`model.simple/complex` 留空走默认模型，先把路由判定正确性落地；有第二模型配额再配模型名。
- **Q2** 阈值默认值（40 字 / 3 轮 / 200 字 / 深度动词表）是否可接受？可调，配置化。

## 4. 任务拆解

| # | 任务 | 级别 | 验证 |
|---|---|---|---|
| K13-1 | gen-repomap.cjs 阶段 1（fs 扫描三语 + 输出 repo-map.md） | L2 | 脚本 EXIT=0 + 抽查命中 + 体积阈值 |
| K13-2 | 二期 tree-sitter 升级（评估后决定） | L2 | 同上 + 依赖审查 |
| P12-1 | AgentOrchestrator.complexity + 配置 + 单测 | L2 | mvn test |
| P12-2 | AiChatService 模型选择接线 + 回归 | L2 | mvn test 全量 |

## 5. Rollback Strategy

- K13：独立脚本 + 独立输出文件，停用即回滚，不碰源码与 CI。
- P1-2：配置留空即回退默认模型；代码单 commit revert 即回退，不碰 AgentType/降级链。

## 6. Not Doing

- K13 不挂 CI 门禁、不做全量 AST 序列化。
- P1-2 不做 Graph 工作流（AgentOrchestrator S3 注释保留）、不做 per-query LLM 复杂度分级、不改 AgentType 契约。
