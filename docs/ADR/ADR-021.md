# ADR-021：暂不引入 Redis（修订 ADR-012）

- **Status**: Accepted
- **Date**: 2026-10-17
- **Supersedes**: ADR-012「引入 Redis」；恢复 ADR-011 第 3 条「不引入 Redis」的技术判断

## Context

ADR-012（2026-10-05）判「引入 Redis」，其核心论据**不是技术必然性**，而是两条项目目标：

> 1. 项目目标明确为「简历门面 Agent 项目」
> 2. Redis 在 AI 方向 JD 出现 47 次（词频第 15）

这两条前提此后都变了：

1. **AGENTS.md §1 已定「阶段六（简历）暂缓（用户明确不做）」**——ADR-012 的首要理由被撤销。
2. **代码实测 0 实现**：`backend/pom.xml` 无 `spring-boot-starter-data-redis`，`backend/src/main/java` 全库 0 处 `RedisTemplate` / `@Cacheable`，`docker-compose.yml` 无 redis 服务。ADR-012 承诺的「M1 骨架加 Redis 连通性验证、M2/M3 落地四场景」从未发生；而 `CONTEXT.md` 曾写成「M2/M3 已落地」（漂移，本次一并修正）。

同时 ADR-012 列举的四场景，现状各自已有解：

| ADR-012 场景 | 当前实现 | 是否需要 Redis |
|---|---|---|
| 两级缓存 | Caffeine 本地缓存（文化数据低频、单实例） | 否 |
| AI 语义缓存 | 未实现；其前置的「前缀扩容」已用算式否决（净亏 31%，见 `docs/plans/PLAN-open-items` A3） | 否（现在） |
| 分布式限流 | `RateLimitFilter` 内存滑动窗口（单实例：42.121.125.4 单 ECS） | 否 |
| JWT 黑名单 | JWT 无状态 + 1440min 有效期；登出由前端清 token（安全审计 L4 已接受该风险） | 否 |

## Decision

**暂不引入 Redis。** ADR-011 第 3 条的技术判断恢复有效；ADR-012 标 superseded（保留历史，不删）。

同步执行：

- 不新增 `spring-boot-starter-data-redis` 依赖；`docker-compose.yml` 不加 redis 服务。
- 语义缓存是四场景里唯一有独立收益的一条，随「AI key + 真实流量」一起重新评估，已并入 `docs/plans/PLAN-open-items` D3。

## Consequences

- 基础设施不增加（少一个容器、少一套连接配置与故障模式）。
- 限流/会话在单实例下正确；一旦水平扩展，须先回到本 ADR 重启决策。
- 治理一致性：ADR-012 的 status 与代码现状对齐，不再出现「ADR 说已决策、代码零实现」的脱节。

## Rejected

- **继续 ADR-012（引入 Redis 但无业务使用）**：正是 ADR-012 自己 Rejected 段写的「摆设式引入」。
- **只引入 Redis 做语义缓存**：需 embedding（AI key 未配）+ 相似度阈值（误命中答非所问），当前无流量可验证收益。

## 反转条件（任一成立即重启本决策）

1. 出现多实例水平扩展需求（限流/会话必须跨进程共享）；
2. 语义缓存有 AI key + 真实流量，且能算出净收益（对比 embedding 成本）；
3. 简历/求职目标重启（ADR-012 的原始前提回归）。
