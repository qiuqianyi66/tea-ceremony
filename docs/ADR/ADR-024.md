# ADR-024：A/B 实验与异常指标自动回滚

- **Status**: Accepted
- **Related**: ADR-016（评测 Trace）、ADR-023（多级兜底与分链路熔断）

## Context

企业级「控制爆炸半径」要求：策略改动先按比例灰度，用真实指标判定好坏，异常时自动回退。

当前项目完全没有这个能力：

1. 改 AI 路由策略、改兜底开关、改 prompt 版本，都只能**全量上线**。出问题只能整体回滚容器——分钟级，且回滚会连带把无关改动一起撤掉。
2. 上一轮引入的多级兜底（ADR-023）本身就是「改变失败语义」的改动（502 → 200+degraded），这类改动最需要灰度验证：兜底命中率、错误率、P99 是否真的变好，只能靠对照组数据回答。
3. 后续要做的 Tool Calling 进 chat、ReAct 循环（审计 #9/#10）都会改变回答质量基线。**没有 A/B 能力就没有安全的验证手段**，这是继续演进的前置条件。

## Decision

引入**无状态分桶 + 指标驱动自动回滚**的实验能力：

1. **分桶用确定性哈希，不建 assignment 表**：`floorMod(sha256(expKey + ":" + subjectId), 100) < trafficPercent` → treatment，否则 control。
   - 同一主体永远落同一组（体验不抖），无需存储（无写放大、无一致性维护）。
   - `subjectId` 优先 userId，其次 sessionId；都没有 → **control**（安全默认：配置不全时走旧路径）。
2. **失败安全**：实验不存在 / 状态非 running / 流量为 0 / 主体缺失，一律返回 control。实验系统自身故障不得影响主流程。
3. **判据来自 Trace，不来自新埋点**：variant 写进 `ai_eval_traces.plan_layer`（复用现有 JSONB 列，不加表、不加埋点链路），按 variant 分组算 calls / errorRate / P99。
4. **自动回滚有硬门槛**：任一组样本 < 30 不评估（小样本的 P99 与错误率不可信）；对照组 errorRate 为 null（零样本）时不判超标——**不能把 null 当 0**。
5. **默认守门阈值**：treatment.errorRate − control.errorRate > 0.05，或 treatment.P99 > control.P99 × 1.5 → 自动 stop，`stop_reason` 写具体原因，并发指标 `tea.ab.auto_rollback`。
6. **停止幂等**：重复 stop 不报错；`stopped` 之后不可回到 `running`（要重启就新建实验）——避免"回滚了又被自动拉起"的震荡。

## Consequences

- 新增一张表 `ab_experiments`（V9）。**不建 assignment 表**是有意取舍：省掉写放大与一致性维护，代价是无法按主体追溯历史分组（需要时看 `ai_eval_traces` 里的 variant 快照）。
- `ExperimentGuardService` 每 5 分钟评估一次 running 实验。评估是只读聚合 + 一次状态更新，成本可忽略。
- 分桶结果缓存 30 秒，启停时主动 evict；因此**启停生效延迟 ≤30 秒**，不是"毫秒级"。真正的毫秒级回滚需要网关层路由（见「反转条件」）。
- 灰度中 `AiChatService` 会多一次内存查表（命中缓存时无 DB 访问）。

## Rejected

- **建 assignment 表记录每个用户的分组**：写放大明显，且我们只需要"稳定分组"不需要"分组历史"。
- **用 `String.hashCode()` 分桶**：分布不均（连续 key 低位呈规律），小流量下会出现整段用户被分到同一组。
- **随机分桶（`Math.random()`）**：同一用户每次请求可能换组，A/B 结论不可信，用户也会看到前后不一致的行为。
- **按 IP 分桶**：NAT/移动网络下大量用户共享 IP，大段用户被绑定到同一组。

## 反转条件

出现下列任一情况，升级为网关层流量调度：
- 需要毫秒级回滚（而不是 ≤30 秒）；
- 需要按地域/设备/渠道等请求属性分桶，而非按主体；
- 多实例部署且要求分桶结果跨实例强一致（哈希无状态方案本身满足，但缓存 evict 需要跨实例广播）。
