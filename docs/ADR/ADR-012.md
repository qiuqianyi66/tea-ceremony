# ADR-012：引入 Redis（修订 ADR-011 的"不引入 Redis"决策）

- **Status**: Accepted
- **Date**: 2026-10-05
- **Supersedes**: ADR-011 第 3 条「Redis：不引入」

## Context

ADR-011 于 2026-10-04 定案"不引入 Redis"，理由是：单实例应用、JWT 无状态会话、Caffeine 本地缓存对低频文化数据足够、限流用单机内存滑动窗口。该决策在"纯技术合理性"视角下成立。

2026-10-05 发生两件事，使该决策的前提发生变化：

1. **项目目标明确为「简历门面 Agent 项目」**——一盏茶的定位是支撑简历、经得起面试深挖的 AI Agent 全栈作品，而非仅以内部技术最优为目标。
2. **重新爬取 AI Agent 方向 JD（721 条，AI 项目经理 / AI Coding / Agent 开发 × 9 城）**：Redis 在 AI 方向 JD 出现 47 次（词频第 15）；旧 Java 后端方向 1349 条调研中 Redis 出现 69 次（第 5 高频）。Redis 是目标岗位明确、反复出现的技能要求。

同时本项目存在 4 个**真实**使用场景（不是为了引入而摆设），这些场景在 Caffeine-only 方案下无法实现或无法在多实例下正确工作。

## Decision

**引入 Redis**，与 Caffeine 配合，落地 4 个真实场景：

1. **两级缓存**：Caffeine 为 L1（本地）、Redis 为 L2（共享），文化数据 / 热点茶叶走 Spring Cache 抽象；先查 L1、未命中查 L2、再未命中回源。
2. **AI 语义缓存**：对 AI 问答/荐茶请求，先用 embedding 相似度匹配 Redis 中的历史响应，命中则直接返回，降低 LLM 调用成本（PRD 风险表已规划"语义缓存"）。
3. **分布式限流**：Redis 滑动窗口计数（用户级 + 全局），替代单机内存方案；天然兼容未来多实例水平扩展。
4. **JWT 黑名单**：登出时将未过期 token 写入 Redis（TTL = token 剩余有效期），在无状态 JWT 方案下实现登出立即失效。

## Consequences

- docker-compose 编排**增加 redis 服务**（backend/frontend/postgres/redis/nginx），`docker-compose.yml` 与部署文档同步更新。
- pom.xml 增加 `spring-boot-starter-data-redis`（连接池用 Lettuce，Spring Boot 默认）。
- **M1 骨架**增加 Redis 连通性验证（健康检查 + 一次读写冒烟）。
- **M2** 落地 JWT 黑名单 + 两级缓存；**M3** 落地语义缓存与限流。
- 每个场景必须有真实代码路径与测试；禁止"只配一个 Redis 连接但没有任何业务使用"的摆设式引入。
- ADR-011 第 3 条在原文标注"已被 ADR-012 修订"，保留历史不改写。

## Rejected

- **继续不引入 Redis（维持 ADR-011）**：与简历目标和 JD 词频（47/69 次）相悖，且 4 个真实场景缺失。
- **只用 Caffeine**：限流与语义缓存无法跨进程共享，多实例扩展时需重做。
- **引入 Redis 但无真实场景**：属于简历注水，且多一个无收益的基础设施，明确禁止。
