# ADR-020：SFT 微调纳入执行范围（推翻「只出概念文档」）

- **Status**: Accepted
- **Date**: 2026-10-10
- **Supersedes**: `docs/plans/PLAN-final-convergence-2026-10-09.md` L224 与 `docs/prd/REQ-ai-project-2026-10-09.md` L117 的「不做模型训练/SFT/RL」条款

## Context

原决策于 2026-10-09 定案：

> **模型训练 / SFT / RL：只出一页概念文档**（能讲清训练数据长什么样）——`PLAN-final-convergence` L224
> **不做模型训练/SFT/RL**：文章要求"了解原理"即可 —— `REQ-ai-project` L117

该决策在当时的约束下自洽：目标是「改造成可进简历的 AI 项目」，改造重头定为**评测体系**（`REQ-ai-project` L13），微调被排除以收缩范围。

触发重评的三项新事实（均为 2026-10-10 实测）：

1. **v5 评测暴露安全风险**：`CHA-003` 的考点「不夸大功效」是 `veto: true`，而回答给出「茶可助消脂」并引《本草纲目》——**prompt 层的安全叮嘱不足以稳定约束模型**（overall 0.80 / pass^1 35/50）。

2. **失败归因显示「知识」不是瓶颈**：15 条失败中 11 条是 prompt/产品逻辑问题，0 条是「模型知识不够」。同时 `culture_chunks = 0`（RAG 向量表空）说明另一短板是**数据没注入**，而非模型能力。
   → 两条线索共同指向：**prompt 不稳（需固化）+ 知识未注入（需填充）**，这是 SFT 的典型适用场景。

3. **能力缺口自认**：`REQ-ai-project` L23 自评「AI 特有：懂概念/懂原理/会评测/能做 Demo」——原决策把「会微调」排除在外，**成为能力矩阵的缺口**。

4. **用户拍板**：2026-10-10 明确「可以百炼微调，我愿意花费」。

## Decision

**SFT 微调纳入执行范围**，但严格限定：

1. **只做 SFT-LoRA**（百炼平台支持的高效微调）——不做 RL / DPO / 全参微调。
2. **只微调现有 qwen 系列**——不训练全新模型。
3. **先单专家验证**（mentor，评测失败最多），达标再考虑推广。
4. **预算受护栏约束**（决策 D-5，待用户给定上限）。
5. **效果未达标不上线**——留出集不优于 base 则如实记录失败原因。
6. **微调前必须有可信基线**（Phase 3 的 pass^3 + judge 一致率）——否则无法证明微调有效。

**执行顺序**（`docs/plans/PLAN-ai-capability-2026-10-10.md`）：
```
Phase 1 安全边界 → Phase 2 知识注入 → Phase 3 评测基线 → Phase 4 SFT → Phase 5 缓存
```
关键理由：Phase 1/2 的产物**同时是 Phase 4 的语料**（修 prompt 的「正确答案」= 高质量 SFT 样本），故不是串行堆叠而是同一份工作两个用途。

**本 ADR 覆盖范围**：仅推翻 SFT/微调条款。原决策中「不做多 agent 接力流水线」「不引入 promptfoo/DeepEval」等其他 Not Doing 条款**继续有效**。

## Consequences

- `PLAN-final-convergence` L224 与 `REQ-ai-project` L117 两处原文需**同步更新**（否则文档自相矛盾）。
- 引入**付费依赖**：百炼 SFT 训练 + 部署按量计费，且**训练费不可退**。缓解 = 预算护栏 + 先单专家 + 留出集验证。
- 引入**新的失败模式**：微调可能导致非茶领域能力退化（灾难性遗忘）。缓解 = 留出集含通用对话样本 + 模型名可配置随时切回 base。
- 新增能力矩阵条目：**会微调**（原缺口）。
- 简历素材扩展：从「会评测」到「会评测 + 会微调」，且**有真实对比数据**（base vs 微调）。

## Rejected

- **维持原决策（只出概念文档）**：用户已拍板 + 能力缺口成立 + 有真实用途（固化安全边界），维持即与用户意图冲突。
- **全参微调 / 训练新模型**：数据量差 3-4 个数量级（实测仅 704 条调用 / 4 用户），全参必然过拟合；LoRA 成本低一个数量级且够用。
- **跳过 Phase 3 直接微调**：无基线则无法证明微调有效，且会掩盖「prompt 本可修复」的问题——先用最便宜手段（prompt）解决能解决的。
- **五专家一起微调**：预算浪费，且首批必然踩坑；单专家验证流程更稳。
- **用微调替代 RAG 填数据**：二者痛点不同——RAG 治「不知道」，微调治「不稳定/贵」。当前 `culture_chunks = 0`，RAG 优先级更高。
