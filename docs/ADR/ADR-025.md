# ADR-025：Prometheus 指标导出与告警栈

- **Status**: Accepted
- **Related**: ADR-016（评测 Trace）、ADR-022（匿名遥测）、ADR-023（多级兜底）、ADR-024（A/B 灰度）

## Context

ADR-023/024 落地后，系统已经产生了一批有价值的运行时计数：

| 埋点 | 含义 |
|---|---|
| `tea.ai.call.attempts{lane,outcome}` | 每个专家链路的每次尝试与结果（六种 outcome） |
| `tea.ai.fallback.hit{rule}` | 本地规则兜底命中 |
| `tea.ai.call.depth.exceeded` | 递归深度保护触发 |
| `tea.ab.auto_rollback{exp}` | 实验被守门自动回滚 |
| `tea.ai.toolcalling.*` | Tool Calling 调用与回落 |
| `tea.ai.trace.save.failed` | 观测数据自身落库失败 |
| `tea.culture.search.vector.degraded{reason}` | 向量检索降级 |

但这些数据**只存在于进程内存**：`spring-boot-starter-actuator` 不含 Prometheus registry，`management.endpoints.web.exposure.include` 只有 `health,info`。结果是——

- 指标能算不能看：出事时没人知道，异常只写日志；
- 自动回滚发生了也没人收到通知：守门机制把实验停了，但运维不知道"为什么昨天那个实验自己关了"；
- `trace.save.failed` 这种"观测自损"信号最危险：调用照常，看板数字停在过去，**看板在骗人却显示绿色**。

## Decision

1. **加 `micrometer-registry-prometheus`（runtime scope）并暴露 `/actuator/prometheus`。**
   只加 actuator 不够——Prometheus registry 是独立的可选模块，不引入时把 `prometheus` 写进 exposure 也只会 404。
2. **指标端点不做鉴权，靠网络边界保护**：
   - `backend` 端口绑定改为 `127.0.0.1:18080:8080`（此前是 `18080:8080`，等于把 8080 直接暴露公网，绕过 nginx 的安全头与限流）；
   - nginx 路由白名单只放行 `= /actuator/health`，其余 `/actuator/*` 一律 404；
   - Prometheus 从宿主机回环抓取。
   Prometheus 的抓取协议不支持自定义鉴权头之外的方式，给它加 JWT 会引入一套专用凭据而且明文传输依然存在。收窄网络可达面是更小、更可靠的边界。
3. **告警栈是可选 overlay**，用 `deploy/observability/docker-compose.observability.yml` 叠加，不并入主 compose。
   理由：站点能否运行不依赖监控容器。把监控放进默认服务，会把"监控挂了"变成"站点起不来"——可用性被监控拖累，方向反了。
4. **告警阈值分两类**：
   - 有依据的：延迟阈值取 `application.yml` 的 SLO 常量与 `AiCallExecutor` 的 20s 硬超时；
   - 无依据的（错误率、兜底率）：标为初始值，**上线观察一周拿到真实分布后再收紧**。带着未校准阈值上线，结果一定是告警疲劳，那时真故障就没人看了。
5. **Grafana 看板禁止 UI 编辑**（`allowUiUpdates: false`）：看板必须改仓库 JSON 再重启，否则线上看板与仓库版本漂移，下次重建时改动静默丢失。

## Consequences

- `/actuator/prometheus` 从公网不可达（nginx 404 + 端口只绑回环）。**前提是部署时真的应用了端口绑定**——这是配置项，不是代码保证，CI 的 compose 校验只能验证语法。
- 新增 `deploy/` 目录（prometheus 配置、告警规则、Grafana 看板与 provisioning）。
- 新增 `scripts/verify-alert-rules.cjs` 作为常驻门禁。
- 多一个常驻进程组（Prometheus + Grafana），内存约 300–500MB。单实例 4GB 机器可承受；若资源紧张，Prometheus 可单独部署到另一台。

## Rejected

- **用 `promtool` 做 CI 校验**：项目 CI 环境可拉镜像，但本机网络拉不到 `prom/prometheus`（`auth.docker.io` EOF），导致本地无法复现。改为自己写确定性脚本，**同时校验 promtool 检不出的问题**：指标名与 Java 埋点是否一致（promtool 只校验语法，不校验你引用的指标是否真的存在——而指标名写错是 Prometheus 最典型的静默失效）。
- **给 `/actuator/prometheus` 加 JWT**：Prometheus 抓取不便，且明文端点加鉴权只是把风险从"读到指标"变成"读到令牌"。
- **用 Pushgateway**：单实例短生命周期任务是它唯一的适用场景，我们不适用。
- **把告警接进主 compose**：见 Decision 第 3 条。

## 反转条件

- 多实例部署 → Prometheus 需要服务发现（或每实例用不同端口/标签），static_configs 不再够用；
- 抓取量增长到单机撑不住 → 迁到 VictoriaMetrics / Mimir；
- 需要跨团队分权看板 → 引入 Grafana 组织与团队，`allowUiUpdates` 策略需重新评估。
