# ADR-016：AI 评测四层归因 Trace（append-only 评测底座）

- **Status**: Accepted
- **Date**: 2026-10-09
- **Supersedes**: 无（新增决策）

## Context

AI 项目化改造（REQ-ai-project F-A1）需要"评测能归因"：任务完成率下降时能定位是**输入理解错、上下文缺、路由错还是执行错**（Leo 方法论四层归因）。现有 `ai_usage_logs` 只记成本计量（agent/model/tokens/latency），无内容层、无路由决策、无检索命中快照。

三个设计问题：

1. **归因粒度**：评测失败要能回看该次请求的输入/上下文/规划/执行四层现场，而不只是最终输出。
2. **旁路与承重墙**：Trace 埋点绝不能改变 AI 主流程行为（502 降级承重墙、幂等、会话记忆）。
3. **游客会话**：chat 端点游客可用（前端降级链），游客无 `ai_chat_sessions` 行——Trace 不能强制外键。

## Decision

**append-only 四层归因表 `ai_eval_traces`**：

1. **表结构**（Flyway V5）：`session_id`（可空，游客不引用）、`request_id`（UUID）、`agent_type`、四层 JSONB（`input_layer` 原始问句+意图提示 / `context_layer` 历史锚定条数快照 / `plan_layer` 路由决策 / `exec_layer` 派发与来源数）、`output`、`tokens_in/out/latency_ms`、`error_code`、`created_at`。
2. **旁路记录**：`TraceRecorder`（@Component）begin→complete/fail 生命周期；保存失败仅 warn（同 `AiUsageLogger` 语义），不改主流程。
3. **埋点位置**：`AiChatService.chat()` 单一入口（透明代理与五专家派发共用），不侵入各 agent 内部。
4. **效率数据透传**：`AiChatVo` 增 `tokensIn/tokensOut/latencyMs` 旁路字段（jackson non_null，前端不感知）；`BaseExpertAgent.toVo` 与 `transparentChat` 从 `ChatResponse.getMetadata().getUsage()` 填充。
5. **降级留痕**：502（`BadGatewayException`）→ `error_code=BAD_GATEWAY` + exec_layer 记错误类，评测 adversarial 用例可断言。

## Consequences

- 新表 Flyway V5，up/down 成对（`.harness/changes/ai-eval-trace/`）。
- `AiChatService` 构造器增 `TraceRecorder`（spring 注入，无测试破坏：controller 测试 mock 该 service）。
- 评测器（T11）与 LLM-as-Judge（T12）以本表为数据源；`ai_usage_logs` 继续承担成本计量，不合并。
- 表 append-only，无更新路径；数据量受对话量线性增长（评测期可控，观察后决定归档策略）。

## Rejected

- **复用 `ai_usage_logs` 加列**：混内容层进计量表，语义混杂且缺 session/agent_type 层 → 独立表。
- **agent 内部逐点埋点**：侵入 5 专家 + 透明代理 6 处，回归风险大 → 单一入口。
- **`session_id NOT NULL` 强制引用**：游客 chat 会炸（承重墙）→ 可空外键。
