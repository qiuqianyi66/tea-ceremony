# ADR-028：跨会话用户画像（user_memory 单表 key-value 摘要）

- **Status**: Accepted（v1 单表三类摘要；不做查看/删除端点，留待前端接入切片）
- **Related**: REQ-ai-project-2026-10-09 G-10/F-B2；V12__user_memory.sql；ChatMemoryService（会话级记忆）

## Context

会话级记忆（ai_chat_sessions/ai_messages，V3）只在单会话内生效：用户在会话 A 说「我忌绿茶」，会话 B 开场茶灵不记得。F-B2 要求跨会话记住稳定偏好（偏好茶类/忌口/常用茶器），且守住隐私红线：可查看、可删除、不存敏感信息。

候选结构两条路：

1. **独立宽表**（user_preferences：favorite_tea_type、avoids、favorite_ware… 一列一个字段）——字段随用户谈资无限膨胀，加一类偏好就要改表结构；
2. **单表 key-value 摘要**（user_memory：user_id + key + value，每用户每类一行，value 是 LLM 合并后的一句话摘要）——类别枚举收敛在 CHECK 约束里，内容演进不动表结构。

## Decision

1. **选单表 key-value**：`user_memory(user_id, key, value, source_session_id, …)`，`key ∈ {preference, restriction, habit}`，`uk(user_id, key)` 唯一——每用户每类恒一行。新会话抽取到新信息时，LLM 把「旧摘要 + 本会话新内容」合并成一句新摘要 UPDATE 回去，**不追加行**（摘要不会无限增长）。
2. **否独立宽表**：宽表假设偏好类别可枚举穷尽，实际茶客谈资（口味/水温/器具/场景）不可预知；v1 只要「茶灵记得忌口」这一个故事，宽表的结构化查询收益用不上，却背上 schema 演进成本。
3. **抽取时机 = 旧会话结束**：用户开新会话（无 sessionId）时，对其最近一个旧会话做一次 best-effort LLM 抽取；失败仅 warn，不阻塞聊天承重墙（与 persist 旁路同语义）。抽取结果下一会话后续轮次才注入（本回合 LLM 调用已发出，时序天然晚一拍，可接受）。
4. **注入只放提炼摘要**：新会话开场把三类摘要拼成一段 system 提示注入，**不回灌原始对话消息**——原始消息含闲聊碎片与可能的敏感自述，摘要由 LLM 按「不记录姓名/账号」指令压缩，注入面最小。
5. **隐私红线落地**：抽取 prompt 明令不记录姓名/电话/账号；`source_session_id` 不建 FK（会话级联删除后画像保留，直到用户显式删除）；`UserMemoryService` 提供 list/delete 归属校验方法（`findByUserIdAndKey`），查看/删除端点留待前端接入切片，本 ADR 不扩 controller。
6. **回滚方案**：`DROP TABLE IF EXISTS user_memory CASCADE`（rollback.sql 与 V12 成对）。表是纯新增、无旧表依赖，回滚零数据迁移代价；往返测试 `UserMemoryMigrationRoundTripTest`（Testcontainers 真 PG）：Flyway 启动建表 → 执行 rollback 删表 → 重放 V12 up 重建 → 功能可用。

## Consequences

- 茶灵跨会话记得忌口/偏好；画像表每用户最多 3 行，存储与注入成本恒定。
- 风险：LLM 抽取可能记错或漏记 → 合并写回依赖 prompt 纪律（每类 ≤50 字、空类不动旧行）；记错的修正路径是用户显式删除该类（delete 方法已备）。
- 反转条件：若后续需要按偏好做结构化推荐（如「给忌绿茶的用户推红茶」），再评估从 value 摘要拆出结构化字段；v1 不预建。
