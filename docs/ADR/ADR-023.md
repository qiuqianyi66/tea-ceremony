# ADR-023：AI 多级兜底与分链路熔断

- **Status**: Accepted
- **Related**: ADR-016（评测 Trace）、ADR-018（无 Redis）、ADR-022（匿名遥测）

## Context

企业级生产标准审计（`docs/plans/audit-ai-production-readiness-2026-10-18.md`）查出 AI 层四个硬缺口，其中两个直接决定线上可用性：

1. **执行链路只有「拦截」一段**。`BaseExpertAgent.callLlm()` 与 `AiChatService.transparentChat()` 都是「一次 try/catch → 502」，没有超时、没有重试。上游挂起时 Tomcat 线程被无限占用，P99 不可控，且一次网络抖动就等于一次用户可见失败。
2. **熔断是全局单例**。`AiCircuitBreaker` 只有一个 `openedAt` 与一个计数器，五个专家加透明代理共享。librarian 连续失败 5 次会把 chat/advisor/taster/brewer/mentor 一起熔断——单点故障被放大成整站 AI 不可用。
3. **后端没有本地规则库**。唯一兜底在前端 `src/services/teaAI.ts`。但前端规则引擎拿不到后端数据，且后端不可达时用户的体验是「AI 完全不可用 + 一段通用话术」。
4. 熔断与失败只有日志，没有可量化的指标出口。

## Decision

在 AI 层建立**五段执行链路**，并按链路隔离熔断：

```
深度门禁 → 熔断门禁(lane) → 硬超时 → 指数退避重试 → 本地规则兜底
```

具体决策：

1. **硬超时用虚拟线程**（Java 21），默认 20s，配置化 `tea.ai.resilience.timeout-ms`。不用固定线程池：堵在 IO 上的调用超时后虚拟线程自灭，无需调池大小。
2. **重试只针对可重试异常**：超时、`BadGatewayException`。业务异常（配额/鉴权/参数/不存在）**不重试**——重试业务错误只会把问题放大成流量。默认 3 次，退避 `800ms × 2^(n-1) × (1 ± 20% 抖动)`。
3. **熔断按 lane 分桶**：lane ∈ {chat, librarian, advisor, taster, brewer, mentor}，由类名推导。桶数上界 32，超界归 default 并告警。旧无参 API 保留（→ default 桶）以兼容既有测试与入口层快速失败语义。
4. **执行深度门禁**：`ThreadLocal` 计数，默认上限 3，超限直接走兜底。防止「错误路径上的无限推理」把 token 烧穿。
5. **本地规则兜底是第二级，不是唯一级**：上游失败时先查本地规则库；命中 → `200` + `degraded=true` + `sources=["本地规则库"]`；未命中 → 仍然 `502`，前端 `teaAI.ts` 走第三级降级。
6. **三大黄金指标落端点**：`GET /api/v1/ai/metrics/golden`，数据源 `ai_eval_traces`（不是 `ai_usage_logs`——后者只记成功，算不出错误率）。零调用返回 `null` 而非 0；样本 <20 只压 P99。

## Consequences

- **契约语义变化**：`POST /api/v1/ai/chat` 的 502 从「上游失败」收窄为「上游失败**且**本地规则库未命中」。`AiChatVo` 新增可选字段 `degraded`（null 时 json 不出现，旧客户端无感）。
- **承重墙保留**：`teaAI.ts` 降级链未改动；规则未命中时 502 照旧抛给前端。三級兜底链条完整（本地规则 → 502 → 前端规则）。
- **Trace 口径不变**：兜底命中时 Trace 仍记 `error_code`（上游确实失败了）。指标必须如实反映上游健康度，不能因为「兜住了」就记成功。
- **新增可观测面**：`tea.ai.call.attempts{lane,outcome}`、`tea.ai.call.depth.exceeded`、`tea.ai.fallback.hit{rule}`。
- **成本影响**：重试会把上游失败时的调用次数放大到最多 3 倍。这是有意的取舍——上游失败的请求本来就没拿到结果，3 次里成功 1 次就赚回用户价值；熔断与入口门禁保证失败风暴不会真的打满 3 倍。

## Rejected

- **上 Spring Retry / Resilience4j**：项目无 Redis（ADR-018），且现有 `AiCircuitBreaker` 已能承载分桶改造；引入框架只为一个执行器不划算（YAGNI）。
- **重试所有异常**：业务错误重试会放大流量且必然再次失败。
- **兜底直接返回 200 而不管是否命中**：会让「AI 挂了」对用户完全不可见，也让指标失真。
- **在网关层做兜底**：拿不到问题语义，只能返回通用话术，不如后端按茶数据作答。

## 反转条件

出现下列任一情况重新评估：
- 引入多实例部署 → lane 维度的熔断状态需跨进程共享，改为 Redis 或网关层；
- 上游成本结构变化使「3 倍重试」不可接受 → 降为 2 次并把退避拉长；
- 兜底命中率长期过低（<5%）→ 说明规则库与真实提问分布不匹配，应重做规则而不是加大兜底。
