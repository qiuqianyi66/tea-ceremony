# 通用 Token 优化方案

> 工具无关（Cursor / Claude Code / Codex / Copilot / 豆包 / ChatGPT 均适用）。
> 核心结论：**省 token 靠结构，不靠语气。**

## 0. 一句话结论

一次请求的 token 花在五处：常驻上下文、按需加载、会话历史、工具输出、生成输出。

- 前两处由**文件结构与加载规则**决定——改一次，长期省，与使用者习惯无关。
- 后三处由**单次任务习惯**决定——每次省，但依赖自觉。
- 所以优先级是：先改结构，再改习惯，最后才是调提示词语气。

ROI 排序：

| 序 | 措施 | 典型收益 | 代价 |
|---|---|---|---|
| 1 | 常驻规则瘦身 + 按需加载取代全量加载 | 单次会话输入省 30%–70% | 一次性整理成本 |
| 2 | 一任务一会话 + 关键节点压缩历史 | 长会话省 50% 以上 | 需手动开新会话 |
| 3 | 限制输出（禁注释 / 文档 / 总结；局部改动只给片段） | 输出省 40%–80% | 需求必须写清 |
| 4 | 精确引用上下文（@文件）+ 忽略无关目录 | 输入省 20%–50% | 需知道该喂哪个文件 |
| 5 | 任务分级（廉价模型 / 免费工具 / 用 IDE，而不是都问强模型） | 单价差 5–20 倍 | 需路由判断 |

「暴躁指令」「辱骂」「恐吓」这类语气技巧 ROI 最低、风险最高，见 §5。

## 1. 成本结构

```
输入 = 常驻层（每次必带）            ← 由文件结构决定
     + 按需层（技能/文档/Wiki）      ← 由触发规则决定
     + 会话历史（每轮累积）          ← 由会话管理决定
     + 工具输出（读文件/搜索/命令）  ← 由检索习惯决定
输出 = 生成内容（含废话、注释、总结）← 由输出约束决定
```

关键事实：**输入按轮次重复计费，输出只计一次。** 常驻层多 1 万 token，一个 20 轮的会话就是 20 万 token 输入——这是最大的一笔隐形开支，也是唯一能一次性根治的一笔。

| 来源 | 谁决定 | 特性 | 主要手段 |
|---|---|---|---|
| 常驻层 | 规则文件作者 | 每轮重复 | 瘦身、分层、机械化体检 |
| 按需层 | 技能路由设计 | 命中才付费 | 索引常驻、正文按需、限制一次加载份数 |
| 会话历史 | 使用者 | 线性增长 | 分解会话、压缩、丢弃无用工具输出 |
| 工具输出 | 使用者 | 单次但量极大 | 窄化搜索、限量读取、大输出落盘 |
| 生成输出 | 使用者 | 单价最高 | 明确输出边界、格式约束 |

## 2. 六个控制层

### L0 常驻层：每次都被读的规则文件

目标：只放「每一次任务都必须遵守」的约束。

1. 操作细节、命令、流程步骤、案例、研究笔记——全部移出常驻文件，改为按需读取。
2. 给常驻文件设硬上限（例：单文件 ≤ 300 行 / ≤ 1.5 万 token），超了就地修剪。
3. 同主题合并；新说法覆盖旧说法；禁止同一规则在两份文件里各写一遍。
4. 用脚本做机械化体检（检查行数、失效引用、路径漂移），别靠人记得。
5. 修剪时执行「删除测试」：删掉这一行，AI 会犯错吗？不会就删。
6. 每记一次教训先问：这是操作细节吗？是就进按需文件，不进常驻层。

反面模式：常驻文件里塞大表格、长清单、历史更新记录、示例代码。这些内容的读取频率远低于它们的体积。

### L1 按需层：技能 / 文档 / 知识库

目标：加载进上下文的，只有本次任务真正需要的。

1. 分层标准是「何时被读取」，不是「属于哪个功能」。
2. 常驻一份**短索引**（路由表：一句话 + 路径），正文按需加载。
3. 单次任务限制加载份数（例：≤ 3–4 份），并在规则里写死这个上限。
4. 索引项必须写清触发条件，否则模型会全量扫描来找。
5. 禁止把按需文件的内容抄回常驻文件——那是双重付费加双重维护。

### L2 会话层：对话历史

目标：让历史线性增长变成可控增长。

1. **一任务一会话。** 复杂任务按阶段拆分（方案设计 / 核心开发 / 扩展功能），每阶段一个新会话。
2. 阶段间用一份四行交接（目标 / 已改文件 / 未决问题 / 下一步）替代继承全部历史。
3. 长会话在里程碑处压缩（`/compact`、`/summarize`）。压缩后保留：目标、已改文件清单、未决问题、下一步命令。
4. 工具输出只留结论行；大段日志、完整文件内容、搜索结果原始列表不进历史。
5. 出现「改了 A 又弄坏 B」的来回拉扯，立刻开新会话，不要死磕——这是上下文污染，不是模型变笨。
6. 超过阈值时注意计价台阶：部分服务对超长输入（如 20 万 token 以上）提高单价。

### L3 工具层：读文件 / 搜索 / 命令

目标：单次工具返回别吃掉几千 token。

1. 搜索加过滤（限定目录、文件类型、glob），不要全库裸搜。
2. 读文件带偏移和行数上限，不要整目录读、不要读二进制和大 JSON。
3. 命令输出重定向到文件，只回读尾部或摘要行。
4. 配置忽略文件，排除 `node_modules/`、`.git/`、`dist/`、`build/`、`.venv/`、`*.log`、`test-results/`、密钥文件。
5. 别让模型重新读它刚写过的文件——写入即已知内容。

### L4 输出层：生成内容

目标：付费买代码，不买排版和客套。

1. 默认禁止：注释、文档、README、测试、示例、总结、使用说明（除非明确要求）。
2. 局部改动只输出改动的函数或片段，不重发整个文件。
3. 用格式约束代替长度恳求：「一行一条」「只给 diff」「表格」比「写短点」有效得多。
4. 评审、报告类输出用压缩格式（`文件:行 严重度 问题 → 修复`），信息密度高且省 token。
5. 禁止复述需求、禁止方案罗列——要最优解，不要选择题。

### L5 分配层：这活该不该给 AI

目标：不为机械劳动付 token。

1. 需要理解代码库上下文、需要多轮交互的任务 → 用强模型 / 强工具。
2. 不需要代码库上下文的一次性任务（写文档、解释概念、生成测试数据）→ 用免费工具，不烧额度。
3. 机械劳动（脚手架初始化、批量重命名、格式化、重排文件）→ 用语言自带工具、IDE 重构、脚本。
4. 复杂任务先要方案：确认方向后再写码。方向错一次，浪费的是全量返工成本。
5. 简单问答与复杂分析分开路由（不同模型档位），不要同一模型一视同仁。
6. 若服务支持上下文缓存，把固定前缀做到缓存最小长度以上（常见阈值 1024 token），否则折扣永远吃不到。

## 3. 可复制模板

### 3.1 省钱规则模板

放进 Cursor Rules / `AGENTS.md` / `CLAUDE.md` / 系统提示。按需删改条目，保持短。

```markdown
## Token 纪律（优先级高于默认行为）

输出：
- 只产出被要求的东西；禁止注释、文档、README、测试、示例、总结、使用说明（明确要求时除外）。
- 禁止复述需求、禁止开场白与结束语、禁止「是否需要…」式反问。
- 局部修改只给改动的函数或片段，不重发整个文件。
- 不做多方案罗列，直接给最优解；要排序时用表格或一行一条。

行为：
- 只做明确要求的事；不顺手重构、不顺手加功能、不顺手格式化。
- 不新增依赖、不改架构、不改无关文件。
- 需求不清时只问最关键的一个问题，不写假设清单。
- 复杂任务先给方案，确认后再写码。

上下文：
- 只读完成任务必需的文件；不整目录扫描，不全库搜索。
- 大输出写入文件，只回读结论行。

违反任一输出规则，视为本次任务失败并需重做。
```

最后一句是**可执行后果**，不是恐吓——不写动物、不写诅咒、不做人身攻击，那些既不增加遵从度，又让输出带情绪。

### 3.3 任务提示词骨架

```
目标：<一句话，可验收>
范围：只改 <文件/函数>；不动 <不相关模块>
技术约束：<技术栈 / 代码风格 / 沿用现有模式>
上下文：@<文件1> @<文档1>
不要：注释 / 测试 / 文档 / 重构 / 新依赖
验证：<命令>
产出：<片段 / 整文件 / 方案>
流程：<直接做 / 先给方案>
```

写作要点：目标可验收（能判断做没做对）；范围双向写（改什么 + 不碰什么）；约束具体到文件风格；上下文用引用而不是描述。

### 3.4 会话分解与交接

```
阶段          会话        输入
方案设计      会话 A      需求 + 现状
核心开发      会话 B      方案 + 相关文件
扩展功能      会话 C      方案 + 已完成接口

阶段间交接（四行，替代继承全部历史）：
目标：<本阶段要达成什么>
已改：<文件清单 + 一句话改了什么>
未决：<待定问题 / 待确认假设>
下一步：<具体到命令或文件名>
```

### 3.5 压缩提示词

```
压缩以上对话，只保留：
1) 当前目标与验收标准
2) 已修改文件清单及改动要点
3) 未决问题与已确认的决策
4) 下一步的具体动作
删除：客套、试错过程、完整文件内容、命令原始输出。
用最短的条目式表达。
```

## 4. 度量：怎么确认真的省了

没有测量就没有优化，只会有感觉。

1. **基线三数**（一次性）：常驻层总量、单任务平均输入 token、平均输出 token。
2. **估算口径**（没有 tokenizer 时）：`ASCII 字符数 ÷ 3.8 + 中日韩字符数 ÷ 1.5`。这是保守估算，标注为估算值，不要当实测值报。
3. **改造验收**：改结构前后跑同一个任务，比较输入 token，而不是比较「感觉快了」。
4. **回归检查**：省 token 的手段不得降低产出质量。输出精简对日常问答收益明显，对复杂开发任务可能伤质量——按场景开关，不要全局常开。
5. **指标取不到时报「未测」**，不要记 0。把「没测到」读成「正常」是最常见的失败模式。
6. **缓存类收益要验证命中**：确认响应里的缓存命中计数字段大于 0，再宣称省了钱。

## 5. 流行技巧审查

| 技巧 | 判定 | 依据 |
|---|---|---|
| 禁止 AI 做无用功（禁注释/文档/测试/总结） | 采纳 | 输出侧最大单项节省，可写进规则文件机械化执行 |
| 明确需求、加技术约束 | 采纳 | 减少返工轮次，省的是整轮成本 |
| 先要方案、确认后执行 | 采纳 | 方向错误的返工成本远高于方案本身的 token |
| 手动控制上下文（@引用 + ignore 文件） | 采纳 | 输入侧直接削减，效果可测 |
| 避免历史过长（拆会话 / 压缩） | 采纳 | 输入按轮重复计费，收益随会话长度放大 |
| 能自己做的不交给 AI | 采纳 | 机械劳动的 token 花费本就无产出 |
| 装现成的精简输出技能 | 有条件采纳 | 日常问答省 token 明显；复杂开发任务可能过度影响代码质量，按场景启用 |
| 暴躁指令、辱骂、语气施压 | 不采纳 | 未实测到稳定收益；本质是「约束明确」在起作用，而约束明确有更可靠、可审计的写法。对代码质量与协作记录有负面影响 |
| 恐吓式后果（不听话就发生坏事） | 不采纳 | 行为不可预测，可能触发拒绝或降质；不可审计、不可复现 |
| 「奶奶漏洞」等角色扮演绕过 | 不采纳 | 依赖绕过安全策略，模型版本一更新即失效；生产环境不可用 |

关于语气类写法的诚实说明：**本次未做 A/B 实测**，因此不给出量化收益。可确定的只有一点——把同样的约束写进规则文件（机制层）比每轮靠语气施压（表达层）更稳定，因为前者与使用者当时的心情无关。

## 6. 落地清单

一次性（结构层，做一次长期受益）：

- [ ] 统计常驻文件体积，给硬上限
- [ ] 把操作细节、命令、案例迁出常驻文件
- [ ] 建立短索引 + 按需正文的技能目录
- [ ] 配置忽略文件，排除依赖产物与密钥
- [ ] 写下本项目的省钱规则（§3.1 模板）
- [ ] 记录基线三数

每任务（习惯层）：

- [ ] 新任务开新会话；阶段切换做四行交接
- [ ] 用 §3.3 骨架写提示词，上下文用 @ 引用
- [ ] 复杂任务先要方案
- [ ] 长会话在里程碑处压缩
- [ ] 大输出落盘，只回读结论

每月（体检层）：

- [ ] 跑一次常驻层体积与失效引用检查
- [ ] 复核上月的「省钱手段」是否伤到产出质量
- [ ] 清掉过期的临时规则与死引用

关键读数：

1. **行数护栏会失真**：§13 学习记录一度占 AGENTS.md 的 51.7%，而文件只有 261 行——看似落在「200-350 行」维护区间内，实际 token 密度是同规模文件的 2-3 倍。**行数不能替代 token 度量**，这正是新增预算脚本的原因。
2. **分轮迁移**：每轮各 ≤40% 降幅（仓库既有护栏），每轮后跑一致性体检 + 引用同步，再进下一轮。
3. **零丢失双向校验**：R2 原始 48 条 → `lessons.md` 原文命中 41 条 + AGENTS.md 常驻保留 7 条 = 丢失 0；反向检查 0 条非原文（证明未改写）。R5 同法机械化：`.harness/changes/r5-context-budget/ledger.json` 台账 107 个锚点 + 基线 sha256，`node scripts/audit-context-migration.cjs` 核对命中数（26 项清单与 7 条里程碑为逐行原文命中）。
4. **防反弹门禁**：`scripts/audit-context-budget.cjs` 超预算即 error，已挂 `npm run verify` → `npm run quality` → CI frontend job。R5 后总预算棘轮收紧 21,000 → 19,500，并给三个被压文件加单文件预算。
5. **边际收益递减（R5 实测）**：去掉跨文件重复与派生清单后，剩下的基本都是单行短规则——继续压就得删规则或整域外置（治理决策，不是机械改写）。R5 单轮 −7.3%（四个文件合计 −1,472 token），总计 −27.7%，这是这一层的合理终点。
6. **压缩会暴露规则漂移（R5 实测）**：搬动规则时逐条核对实现，抓到 3 处「规则说的和代码不一样」——§25 构建规则（手动 chunk/200KB 告警 vs `vite.config.ts` 实测 `chunkSizeWarningLimit: 1000`）、图标库（DESIGN_SPEC 写 Iconify vs 实际 `lucide-vue-next`）、异常基类名（规则 `BusinessError` vs 代码 `BusinessException`）。均已按实现对齐；**这类漂移不压缩就永远不会有人看**。
